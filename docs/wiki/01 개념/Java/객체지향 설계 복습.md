# 객체지향 설계 복습

## Java 객체 생성자 캡슐화 복습

### 8. 놓치기 쉬운 핵심

| 번호 | 헷갈리기 쉬운 표현 | 정확한 개념 |
|---:|---|---|
| 1 | 클래스 ≠ 객체 | 클래스는 설계도, 객체는 생성된 인스턴스다. |
| 2 | 참조 변수 ≠ 객체 | `p1`은 객체를 가리키는 변수다. |
| 3 | this ≠ 생성자 전용 | `this`는 현재 객체를 가리키며 non-static 메서드에서도 사용한다. |
| 4 | identityHashCode ≠ 메모리 주소 | 객체 identity 기반의 해시값이다. |
| 5 | String 재대입 ≠ 객체 내부 수정 | String은 immutable이고 참조가 다른 String으로 바뀐다. |
| 6 | GC 대상 ≠ 즉시 삭제 | 실제 수거 시점은 JVM이 결정한다. |
| 7 | 생성자는 상속되지 않음 | 자식 객체 생성 과정에서 부모 생성자는 호출된다. |


## 자바 상속과 객체 설계

### 절차지향과 책임 기반 객체 설계

> 절차 중심 코드는 실행 순서를 중심으로 작성하고, 객체지향 설계는 기능과 책임을 객체별로 분리하여 유지보수성과 확장성을 높입니다.

절차 중심 방식에서는 입력, 난수 생성, 조건 판별, 결과 출력과 같은 기능을 하나의 흐름으로 작성하는 경우가 많습니다.

간단한 프로그램에서는 이해하기 쉽지만 기능이 많아질수록 하나의 메서드나 클래스가 지나치게 많은 역할을 담당할 수 있습니다.

객체지향 설계에서는 기능을 실행 순서가 아니라 책임 단위로 나눕니다.

예를 들어 가위바위보 게임을 다음처럼 구분할 수 있습니다.

| 객체         | 주요 책임                |
| ---------- | -------------------- |
| `Computer` | 난수를 이용하여 컴퓨터의 선택 생성  |
| `Player`   | 사용자 입력 처리 및 선택 값 관리  |
| `Referee`  | 두 선택을 비교하여 승패 판정     |
| `GameMain` | 객체를 생성하고 전체 실행 흐름 제어 |

이렇게 책임을 분리하면 변경이 필요한 부분을 특정 객체 중심으로 수정할 수 있습니다.

예를 들어 승패 규칙이 바뀌면 `Referee`를 중심으로 수정하고, 입력 방식이 바뀌면 `Player`를 중심으로 수정할 수 있습니다.

이러한 설계는 SOLID 원칙 중 단일 책임 원칙(SRP)과도 연결됩니다.

단일 책임 원칙은 하나의 클래스가 가능한 한 하나의 주요 책임 또는 하나의 변경 이유를 가지도록 설계하는 것을 의미합니다.


### 전체 핵심 정리

이번 학습 내용은 다음 흐름으로 연결해서 이해할 수 있습니다.

```text
참조형 데이터
   ↓
배열과 객체는 주소를 통해 참조
   ↓
얕은 복사와 독립 복사의 차이
   ↓
String Pool과 == / equals()
   ↓
객체를 책임 단위로 설계
   ↓
클래스와 인터페이스로 역할 분리
   ↓
extends / implements
   ↓
abstract / final / sealed로 구조 제어
   ↓
다형성을 이용해 공통 타입으로 여러 객체 처리
```

특히 중요한 부분은 다음입니다.

1. 참조형에서 `==`는 같은 객체를 참조하는지 확인합니다.
2. 문자열 내용 비교에는 `equals()`를 사용합니다.
3. 클래스 상속은 하나만 가능하지만 여러 인터페이스를 구현할 수 있습니다.
4. 추상 클래스는 공통 상태와 구현을 제공할 수 있습니다.
5. 인터페이스는 공통 규약을 정의하는 데 적합합니다.
6. `sealed`는 허용된 하위 타입을 제한할 수 있습니다.
7. 상속은 단순 재사용보다 타입 관계와 책임을 기준으로 설계하는 것이 중요합니다.
8. 공통 상위 타입으로 서로 다른 하위 객체를 다루는 구조가 다형성의 핵심입니다.
