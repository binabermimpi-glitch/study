
# 정보처리기사 실기 - 관계 대수·관계 해석·블랙박스 테스트·인터페이스 통신

# 1. 관계 대수 (Relational Algebra)

## 출제 이력

- 2022년 3회 실기
- 순수 관계 연산자 관련: 2020년 3회, 2022년 2회, 2023년 3회, 2025년 2회 실기

## 관계 대수란?

관계 대수는 관계형 데이터베이스에서 원하는 데이터를 얻기 위해 사용하는 **절차적 질의 언어**입니다.

- 어떤 데이터를 검색할 것인지 정의
- 어떤 연산을 수행하여 결과를 얻을 것인지 표현
- 연산의 입력과 출력은 릴레이션
- 일반 집합 연산자와 순수 관계 연산자로 구분

관계 대수의 연산자는 크게 두 가지로 나뉩니다.

1. 일반 집합 연산자
2. 순수 관계 연산자

---

# 2. 일반 집합 연산자

수학의 집합 이론을 기반으로 하는 연산자입니다.

합집합, 교집합, 차집합은 두 릴레이션이 **합병 가능(Union-compatible)** 해야 합니다.

### 합병 가능 조건

1. 두 릴레이션의 애트리뷰트(속성) 개수가 같아야 함
2. 대응되는 애트리뷰트의 도메인이 호환되어야 함

※ 카티션 프로덕트는 합병 가능 조건이 필요하지 않습니다.

| 연산자 | 기호 | 설명 |
|---|---|---|
| 합집합 | ∪ | 두 릴레이션의 모든 튜플을 반환 (중복 제외) |
| 교집합 | ∩ | 두 릴레이션에 공통으로 존재하는 튜플 반환 |
| 차집합 | − | 첫 번째 릴레이션에만 존재하는 튜플 반환 |
| 카티션 프로덕트 | × | 두 릴레이션의 모든 튜플 조합 반환 |

## 카티션 프로덕트 (Cartesian Product)

두 릴레이션의 모든 튜플을 서로 조합하는 연산입니다.

### 릴레이션 R

| 이름 |
|---|
| 김감자 |
| 이고구마 |

### 릴레이션 S

| 과목 |
|---|
| DB |
| 네트워크 |
| 보안 |

### R × S 결과

| 이름 | 과목 |
|---|---|
| 김감자 | DB |
| 김감자 | 네트워크 |
| 김감자 | 보안 |
| 이고구마 | DB |
| 이고구마 | 네트워크 |
| 이고구마 | 보안 |

결과 튜플 수:

2 × 3 = 6개

### 특징

- 모든 튜플을 조건 없이 조합
- 결과 튜플 수 = R의 튜플 수 × S의 튜플 수
- 두 릴레이션의 속성이 달라도 사용 가능
- 조인과 달리 일치 조건을 요구하지 않음

# 3. 순수 관계 연산자

관계형 데이터베이스 모델을 위해 만들어진 연산자입니다.

| 연산자 | 기호 | 설명 |
|---|---|---|
| 셀렉트 (Select) | σ (Sigma) | 조건을 만족하는 행 추출 |
| 프로젝트 (Project) | π (Pi) | 지정한 열 추출, 중복 제거 |
| 조인 (Join) | ⋈ | 두 릴레이션을 결합 |
| 디비전 (Division) | ÷ | 다른 릴레이션의 모든 조건을 만족하는 값 추출 |

## 3-1. 셀렉트 (Select)

릴레이션에서 특정 조건을 만족하는 튜플(행)을 추출합니다.

- 기호: σ
- 수평적 부분집합
- 행을 선택하는 연산

### 예시

학생 릴레이션

| 학번 | 이름 | 점수 |
|---|---|---|
| 100 | 김감자 | 90 |
| 200 | 이고구마 | 70 |
| 300 | 박옥수수 | 85 |

점수가 80점 이상인 학생 검색:

σ(점수 ≥ 80)(학생)

결과:

| 학번 | 이름 | 점수 |
|---|---|---|
| 100 | 김감자 | 90 |
| 300 | 박옥수수 | 85 |

## 3-2. 프로젝트 (Project)

릴레이션에서 원하는 속성(열)만 추출합니다.

- 기호: π
- 수직적 부분집합
- 중복 튜플 제거

### 예시

π(이름)(학생)

결과:

| 이름 |
|---|
| 김감자 |
| 이고구마 |
| 박옥수수 |

※ 관계 대수의 프로젝트는 중복을 제거합니다.

SQL의 SELECT는 기본적으로 중복을 허용하며, 중복을 제거하려면 DISTINCT를 사용합니다.

## 3-3. 조인 (Join)

두 릴레이션에서 결합 조건을 만족하는 튜플을 연결하여 새로운 릴레이션을 만드는 연산입니다.

### 릴레이션 R (학생)

| 학번 | 이름 |
|---|---|
| 100 | 김감자 |
| 200 | 이고구마 |
| 300 | 박옥수수 |

### 릴레이션 S (수강)

| 학번 | 과목 |
|---|---|
| 100 | DB |
| 100 | 네트워크 |
| 200 | DB |

### R ⋈ S 결과

| 학번 | 이름 | 과목 |
|---|---|---|
| 100 | 김감자 | DB |
| 100 | 김감자 | 네트워크 |
| 200 | 이고구마 | DB |

### 실행 원리

- 학번 100: 수강 정보 2개 → 결과 2행
- 학번 200: 수강 정보 1개 → 결과 1행
- 학번 300: 일치하는 수강 정보 없음 → 제외

위 예시는 공통 속성인 학번을 기준으로 결합하는 **자연 조인(Natural Join)** 입니다.

### 조인의 종류

| 종류 | 설명 |
|---|---|
| 세타 조인 (Theta Join) | =, &lt;, &gt; 등의 비교 조건으로 결합 |
| 동등 조인 (Equi Join) | = 조건을 사용하여 결합 |
| 자연 조인 (Natural Join) | 같은 이름의 공통 속성을 기준으로 동등 조인하고 중복 속성 제거 |
| 외부 조인 (Outer Join) | 일치하지 않는 행도 지정된 방향에 따라 포함 |

※ 자연 조인은 같은 이름의 모든 공통 속성을 기준으로 결합합니다.

## 3-4. 디비전 (Division)

디비전은 **다른 릴레이션의 모든 튜플과 관계를 맺고 있는 값**을 추출하는 연산입니다.

기호: ÷

핵심 개념:

"B 릴레이션의 모든 값과 짝을 이루는 A의 값만 추출한다."

### 릴레이션 R (수강)

| 학생 | 과목 |
|---|---|
| 김감자 | DB |
| 김감자 | 네트워크 |
| 김감자 | 보안 |
| 이고구마 | DB |
| 이고구마 | 보안 |
| 박옥수수 | DB |
| 박옥수수 | 네트워크 |

### 릴레이션 S (필수 과목)

| 과목 |
|---|
| DB |
| 네트워크 |

### R ÷ S 결과

| 학생 |
|---|
| 김감자 |
| 박옥수수 |

### 실행 원리

- 김감자: DB O, 네트워크 O → 포함
- 이고구마: DB O, 네트워크 X → 제외
- 박옥수수: DB O, 네트워크 O → 포함

디비전의 핵심은 **모든(ALL)** 입니다.

필수 조건 중 하나라도 만족하지 못하면 결과에서 제외됩니다.

### 디비전은 속성이 2개일 때만 가능한가?

아닙니다.

디비전은 릴레이션의 속성이 3개 이상이어도 가능합니다.

일반적으로 R의 속성 집합을 X ∪ Y, S의 속성 집합을 Y라고 하면:

R(X, Y) ÷ S(Y)

결과에는 X 속성이 남습니다.

### 예시

릴레이션 R (수강)

| 학생 | 학과 | 과목 |
|---|---|---|
| 김감자 | 컴퓨터 | DB |
| 김감자 | 컴퓨터 | 네트워크 |
| 이고구마 | 전자 | DB |
| 박옥수수 | 정보 | DB |
| 박옥수수 | 정보 | 네트워크 |

릴레이션 S (필수 과목)

| 과목 |
|---|
| DB |
| 네트워크 |

R ÷ S 결과

| 학생 | 학과 |
|---|---|
| 김감자 | 컴퓨터 |
| 박옥수수 | 정보 |

### 정리

- R은 3개 속성을 가짐
- S는 1개 속성을 가짐
- 결과는 S의 속성을 제외한 R의 속성으로 구성
- 필수 과목을 모두 만족하는 (학생, 학과) 조합만 반환

※ S의 속성은 R에 포함되어 있어야 하며, 결과는 S의 모든 튜플과 결합된 값이 R에 존재하는지 확인하여 결정합니다.

# 4. 관계 해석 (Relational Calculus)

## 출제 이력

- 2022년 2회 실기

## 관계 해석이란?

관계 해석은 원하는 데이터가 **무엇(What)** 인지만 기술하고, 데이터를 얻는 절차는 DBMS에 맡기는 비절차적 언어입니다.

수학의 술어 논리(Predicate Calculus)를 기반으로 합니다.

관계형 데이터베이스를 제안한 E. F. Codd가 관계 대수와 함께 제시했습니다.

### 관계 대수와 관계 해석 비교

| 구분 | 관계 대수 | 관계 해석 |
|---|---|---|
| 방식 | 절차적 | 비절차적 |
| 핵심 | How (어떻게) | What (무엇을) |
| 기반 | 집합 연산 | 술어 논리 |
| 특징 | 연산 과정을 기술 | 결과가 만족할 조건을 기술 |

관계 대수와 안전한 관계 해석은 표현할 수 있는 질의의 범위가 같습니다.

## 관계 해석의 종류

| 종류 | 변수 | 설명 |
|---|---|---|
| 튜플 관계 해석 | 튜플 | 조건을 만족하는 행을 변수로 사용 |
| 도메인 관계 해석 | 도메인 원소 | 조건을 만족하는 속성 값을 변수로 사용 |

## 4-1. 튜플 관계 해석

튜플 전체를 변수로 사용하여 조건을 표현합니다.

### 예시

학생 릴레이션

| 학번 | 이름 | 점수 |
|---|---|---|
| 100 | 김감자 | 90 |
| 200 | 이고구마 | 70 |
| 300 | 박옥수수 | 85 |

점수가 80점 이상인 학생을 조회:

`{ t | 학생(t) ∧ t.점수 ≥ 80 }`

### 해석

- t: 하나의 튜플
- 학생(t): t가 학생 릴레이션에 속함
- ∧: AND
- t.점수 ≥ 80: 점수가 80 이상

결과:

| 학번 | 이름 | 점수 |
|---|---|---|
| 100 | 김감자 | 90 |
| 300 | 박옥수수 | 85 |

## 4-2. 도메인 관계 해석

튜플 전체가 아니라 개별 속성 값을 변수로 사용합니다.

### 예시

점수가 80점 이상인 학생의 이름을 조회:

`{ n | ∃i ∃s (학생(i, n, s) ∧ s ≥ 80) }`

### 해석

- i: 학번
- n: 이름
- s: 점수
- ∃: 존재한다
- ∧: AND

즉, 점수가 80 이상인 학생의 이름을 반환합니다.

결과:

| 이름 |
|---|
| 김감자 |
| 박옥수수 |

## 관계 해석의 주요 논리 기호

| 기호 | 의미 |
|---|---|
| ∧ | AND |
| ∨ | OR |
| ¬ | NOT |
| ∃ | 존재한다 (EXISTS) |
| ∀ | 모든 (FOR ALL) |
| = | 같다 |
| ≠ | 같지 않다 |

### 시험에서 구분할 것

- 관계 대수 → 절차적 언어
- 관계 해석 → 비절차적 언어
- 튜플 관계 해석 → 행 중심
- 도메인 관계 해석 → 속성 값 중심

# 5. 관계 대수 기출 유형 - 디비전

## 문제

다음 설명에 해당하는 관계 대수 연산자는 무엇인가?

"B의 조건에 맞는 A의 튜플을 추출한다."

특히 B의 모든 튜플과 대응하는 A의 값을 구하는 연산이다.

## 정답

**디비전 (Division, ÷)**

## 해설

A ÷ B는 B의 모든 튜플과 관계를 맺는 A의 값을 추출하고, B의 속성을 제거한 결과를 반환합니다.

핵심 표현:

- B의 모든 튜플
- 모든 조건을 만족
- A에서 해당 값을 추출

이러한 표현이 나오면 디비전 연산을 먼저 생각해야 합니다.

## 오답 보기 분석

| 기호 | 연산자 | 의미 |
|---|---|---|
| σ | 셀렉트 | 조건을 만족하는 행 추출 |
| π | 프로젝트 | 지정한 열 추출 |
| ∪ | 합집합 | 두 릴레이션의 모든 튜플 |
| ∩ | 교집합 | 공통 튜플 |
| − | 차집합 | 왼쪽에만 존재하는 튜플 |
| × | 카티션 프로덕트 | 모든 튜플 조합 |
| ⋈ | 조인 | 결합 조건에 맞는 튜플 연결 |
| ÷ | 디비전 | 모든 조건을 만족하는 값 추출 |
| ρ | 리네임 | 릴레이션 또는 속성 이름 변경 |

### 주의

- A − B와 B − A는 결과가 다를 수 있음
- 프로젝트는 중복 튜플을 제거
- 카티션 프로덕트는 조건 없이 모든 조합 생성
- 조인은 두 릴레이션을 결합
- 디비전은 모든 조건을 만족하는 값을 추출

※ 디비전의 의미는 다른 관계 대수 연산들을 조합해서도 표현할 수 있습니다. 단일 연산자 기호를 묻는 문제에서는 ÷가 정답입니다.

# 6. 블랙박스 테스트 (Black-box Testing)

## 블랙박스 테스트란?

프로그램의 내부 소스 코드나 구현 구조를 확인하지 않고, 요구사항 명세를 기준으로 입력과 출력이 올바른지 검사하는 테스트입니다.

다른 명칭:

- 명세 기반 테스트
- 기능 테스트

### 특징

- 내부 코드 구조를 몰라도 테스트 가능
- 사용자 관점에서 기능 검증
- 입력 조건과 예상 출력 결과를 비교
- 요구사항 충족 여부를 확인

## 주요 블랙박스 테스트 기법

| 기법 | 핵심 특징 |
|---|---|
| 동등 분할 테스트 | 입력 데이터를 유사한 동작을 하는 그룹으로 분류 |
| 경계값 분석 | 입력 범위의 경계 부근을 검사 |
| 결정 테이블 테스트 | 조건 조합과 행동을 표로 정리 |
| 상태전이 테스트 | 상태 변화와 전이 조건 검사 |
| 원인-결과 그래프 테스트 | 입력 조건과 출력 결과의 논리적 관계를 그래프로 표현 |
| 유스케이스 테스트 | 사용자 시나리오의 흐름을 검사 |
| 페어와이즈 테스트 | 모든 파라미터 값의 쌍을 최소 한 번 이상 검사 |

# 7. 원인-결과 그래프 테스트 (Cause-Effect Graph Testing)

## 문제

요구사항의 논리적인 입력 조건과 출력 조건의 발생을 그래프를 활용하여 표현하고, 입력 데이터 간의 관계 및 출력에 미치는 영향을 분석하여 효용성이 높은 테스트 케이스를 선정하여 테스트하는 블랙박스 테스트 기법은 무엇인가?

## 정답

**원인-결과 그래프 테스트 (Cause-Effect Graph Testing)**

※ 제시된 정답 표기 기준에서는 '원인-결과 그래프 테스트'를 사용합니다.

## 해설

입력 조건(Cause)과 출력 결과(Effect)의 관계를 논리 그래프로 표현하여 테스트 케이스를 설계하는 기법입니다.

- Cause: 원인, 입력 조건
- Effect: 결과, 출력 또는 동작
- AND, OR, NOT 등의 논리 관계 사용
- 입력 조건의 조합이 출력에 미치는 영향을 분석

### 예시

회원 등급 승급 조건:

- C1: 누적 구매 금액 50만 원 이상
- C2: 작성 리뷰 10건 이상
- C3: 최근 1년 내 탈퇴 이력 없음
- E1: 골드 등급 승급

조건:

(C1 OR C2) AND C3

즉, 구매 금액이나 리뷰 수 중 하나를 만족하면서 탈퇴 이력이 없어야 승급됩니다.

### 논리 구조

C1 ─┐
    OR ─ I1 ─┐
C2 ─┘        AND ─ E1
C3 ──────────┘

I1은 중간 노드입니다.

### 테스트 케이스

| C1 | C2 | C3 | 승급 여부 |
|---|---|---|---|
| T | T | T | 승급 |
| T | T | F | 승급하지 않음 |
| T | F | T | 승급 |
| T | F | F | 승급하지 않음 |
| F | T | T | 승급 |
| F | T | F | 승급하지 않음 |
| F | F | T | 승급하지 않음 |
| F | F | F | 승급하지 않음 |

### 시험 포인트

다음 표현이 나오면 원인-결과 그래프 테스트를 생각합니다.

- 입력 조건과 출력 결과의 관계
- 논리 그래프
- 원인과 결과
- AND, OR 등 논리 연산
- 그래프를 활용한 테스트 케이스 설계

# 8. 결정 테이블 테스트 (Decision Table Testing)

## 문제

다음은 도서 대출 연장 기능의 검사에 사용한 자료이다.

T는 참, F는 거짓, -는 참·거짓 어느 쪽이든 무관함을 뜻하고, X는 수행할 행동이다.

각 규칙을 하나의 테스트 케이스로 삼아 조건 조합에 따라 올바른 행동이 수행되는지 확인한다.

| 규칙 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| **조건** | | | | |
| 연체 이력이 없다 | T | T | T | F |
| 예약자가 없다 | T | T | F | - |
| 연장 횟수가 2회 미만이다 | T | F | - | - |
| **행동** | | | | |
| 연장 승인 | X | | | |
| 연장 거부 | | X | X | X |

이와 같이 테스트 케이스를 명세할 때 사용된 블랙박스 테스트 기법은?

## 정답

**결정 테이블 테스트 (Decision Table Testing)**

## 해설

결정 테이블 테스트는 여러 입력 조건의 조합에 따라 수행해야 하는 행동을 표로 나타내는 기법입니다.

### 규칙 분석

- 규칙 1: 모든 조건 만족 → 연장 승인
- 규칙 2: 연장 횟수 제한 초과 → 연장 거부
- 규칙 3: 예약자 존재 → 연장 거부
- 규칙 4: 연체 이력 존재 → 연장 거부

### 기호 의미

- T: 참
- F: 거짓
- -: 상관없음
- X: 수행할 행동

### 시험 포인트

- 조건과 행동을 표로 표현
- 여러 조건의 조합 분석
- 규칙별 테스트 케이스 생성

※ 원인-결과 그래프 테스트도 결정 테이블을 활용할 수 있지만, 문제에서 조건과 행동의 조합표 자체를 중심으로 설명하면 결정 테이블 테스트입니다.

# 9. 상태전이 테스트 (State Transition Testing)

## 문제

다음은 현관 도어락에서 검사할 동작 일부이다.

- 잠김에서 번호 입력 시작 → 입력 중
- 번호 일치 → 열림
- 세 번 불일치 → 경보
- 열림에서 문을 닫음 → 잠김
- 경보에서 관리자 해제 → 잠김

각 화살표를 하나의 테스트 케이스로 삼아, 출발 상태에서 사건을 발생시킨 후 도착 상태가 올바른지 확인하였다.

이 테스트 기법은 무엇인가?

## 정답

**상태전이 테스트 (State Transition Testing)**

## 해설

시스템의 상태가 특정 사건이나 조건에 의해 다른 상태로 변화하는지를 검사하는 기법입니다.

### 상태 변화 예시

잠김 → 입력 중 → 열림 → 잠김

또는

잠김 → 입력 중 → 경보 → 잠김

### 주요 요소

- 상태(State): 잠김, 입력 중, 열림, 경보
- 사건(Event): 번호 입력, 문 닫기, 관리자 해제
- 전이(Transition): 하나의 상태에서 다른 상태로 이동

### 시험 포인트

- 상태 변화
- 전이 조건
- 상태 다이어그램
- 이벤트에 따른 상태 변경

# 11. 페어와이즈 테스트 (Pairwise Testing)

## 개념

모든 가능한 입력 파라미터의 조합을 테스트하는 대신, 서로 다른 파라미터 값들의 모든 쌍(Pair)이 적어도 한 번씩 포함되도록 테스트 케이스를 설계하는 기법입니다.

### 목적

- 테스트 케이스 수 감소
- 조합 폭발 문제 완화
- 파라미터 간 상호작용 오류 탐지

## 예시

웹사이트 설정:

- OS: Windows, Mac
- 브라우저: Chrome, Firefox
- 언어: 한국어, 영어

전체 조합:

2 × 2 × 2 = 8개

### 페어와이즈 테스트 적용

| TC | OS | 브라우저 | 언어 |
|---|---|---|---|
| TC1 | Windows | Chrome | 한국어 |
| TC2 | Windows | Firefox | 영어 |
| TC3 | Mac | Chrome | 영어 |
| TC4 | Mac | Firefox | 한국어 |

4개의 테스트 케이스로 모든 두 파라미터 간 값의 쌍을 한 번 이상 검사할 수 있습니다.

### 시험 포인트

- 모든 쌍을 적어도 한 번 검사
- 테스트 케이스 수 최소화
- 조합 폭발 문제 해결

※ 모든 파라미터의 전체 조합을 검사하는 것이 아닙니다.

# 12. 추가 블랙박스 테스트 기법

## 12-1. 동등 분할 테스트 (Equivalence Partitioning)

입력 데이터를 동일한 동작이 예상되는 그룹으로 나누어 대표값을 테스트하는 기법입니다.

### 예시

나이 입력 가능 범위: 20세 ~ 60세

입력 데이터를 세 그룹으로 나눕니다.

- 20 미만: 유효하지 않은 그룹
- 20 ~ 60: 유효한 그룹
- 60 초과: 유효하지 않은 그룹

대표 테스트 값:

15, 30, 70

## 12-2. 경계값 분석 (Boundary Value Analysis)

입력값의 경계 부근에서 오류가 자주 발생한다는 점을 이용하는 기법입니다.

### 예시

나이 입력 가능 범위: 20세 ~ 60세

대표 테스트 값:

19, 20, 21, 59, 60, 61

### 차이점

- 동등 분할: 그룹별 대표값 검사
- 경계값 분석: 경계 바로 앞, 경계, 경계 바로 뒤 검사

# 14. WebSocket (웹소켓)

## 문제

클라이언트와 서버 간의 양방향 실시간 통신을 가능하게 하여, 서버가 클라이언트의 요청 없이도 데이터를 보낼 수 있는(Server-Push) 프로토콜은 무엇인가?

## 정답

**WebSocket (웹소켓)**

## 해설

WebSocket은 클라이언트와 서버 사이에 지속적인 연결을 유지하면서 양방향 통신을 수행하는 프로토콜입니다.

### 특징

- 양방향 통신 (Full-Duplex)
- 실시간 데이터 송수신
- 연결 유지
- 서버가 먼저 메시지를 보낼 수 있음

### HTTP와 WebSocket 비교

| 구분 | 일반적인 HTTP 통신 | WebSocket |
|---|---|---|
| 통신 방식 | 요청-응답 중심 | 양방향 |
| 서버의 선제적 메시지 | 일반 요청-응답 방식에서는 제한적 | 가능 |
| 연결 | 요청마다 처리 | 연결 유지 |
| 대표 용도 | 웹페이지, 일반 API | 채팅, 실시간 알림 |

※ WebSocket은 초기 연결 수립에 HTTP 업그레이드 방식을 사용할 수 있습니다.

### 사용 예시

- 실시간 채팅
- 실시간 주식 시세
- 온라인 게임
- 실시간 알림
- 공동 문서 편집

# 15. GraphQL

## 문제

클라이언트가 필요한 데이터만 정확하게 요청하여 Over-fetching 및 Under-fetching 문제를 해결하는 API를 위한 쿼리 언어는 무엇인가?

## 정답

**GraphQL**

## 해설

GraphQL은 클라이언트가 필요한 데이터의 구조와 필드를 직접 지정하여 요청할 수 있는 API 쿼리 언어입니다.

### Over-fetching

필요하지 않은 데이터까지 너무 많이 받아오는 문제입니다.

예시:

사용자 이름만 필요하지만 서버가 사용자 번호, 이름, 이메일, 주소, 전화번호를 모두 반환하는 경우입니다.

### Under-fetching

한 번의 요청으로 필요한 데이터를 충분히 받지 못해 추가 요청이 필요한 문제입니다.

예시:

사용자 정보와 작성 게시글이 필요한데, 사용자 정보만 받아서 게시글을 별도로 요청해야 하는 경우입니다.

### GraphQL 예시

```graphql
query {
  user(id: 1) {
    name
    email
  }
}
```

이 요청은 사용자의 이름과 이메일만 요구합니다.

### 특징

- 필요한 필드를 클라이언트가 선택
- Over-fetching 감소
- Under-fetching 완화
- API 요청 구조를 유연하게 정의

※ GraphQL을 사용한다고 모든 데이터 요청 문제가 자동으로 해결되는 것은 아닙니다. 서버 스키마와 쿼리 설계에 따라 성능이 달라집니다.

# 16. 인터페이스 통신 기술

## 16-1. AJAX

AJAX는 Asynchronous JavaScript and XML의 약자입니다.

웹페이지 전체를 새로고침하지 않고 비동기적으로 서버와 데이터를 주고받아 일부 화면을 갱신하는 개발 기법입니다.

### 특징

- 비동기 통신
- 페이지 전체 새로고침 없이 화면 일부 갱신
- XMLHttpRequest 또는 Fetch API 활용
- XML뿐 아니라 JSON도 사용 가능

### 사용 예시

- 자동 검색어 추천
- 댓글 등록
- 실시간 검색 결과
- 좋아요 버튼

## 16-2. Fetch API

JavaScript에서 HTTP 요청을 보내고 응답을 처리하기 위한 웹 API입니다.

Promise를 기반으로 비동기 처리를 지원합니다.

### 예시

```javascript
fetch("/api/users")
  .then(response => response.json())
  .then(data => console.log(data));
```

### 특징

- HTTP 요청 처리
- Promise 기반
- async/await와 함께 사용 가능
- AJAX 구현 수단 중 하나

## 16-3. JSON-RPC

JSON 형식의 메시지를 사용하여 원격 프로시저를 호출하는 프로토콜입니다.

### 특징

- JSON 기반
- 메서드명과 매개변수 전달
- 원격 함수 호출
- 요청과 응답에 식별자 사용 가능

### 예시

```json
{
  "jsonrpc": "2.0",
  "method": "sum",
  "params": [10, 20],
  "id": 1
}
```

서버에 sum 메서드 실행을 요청하는 예시입니다.

## 16-4. REST

REST는 Representational State Transfer의 약자입니다.

웹에서 자원을 식별하고 HTTP의 표준 메서드 등을 활용하여 자원을 다루는 아키텍처 스타일입니다.

### 주요 HTTP 메서드

| 메서드 | 역할 |
|---|---|
| GET | 조회 |
| POST | 생성 또는 처리 요청 |
| PUT | 자원 생성 또는 전체 교체 |
| PATCH | 부분 수정 |
| DELETE | 삭제 |

### 예시

```http
GET /users/1
```

사용자 1번의 정보를 조회합니다.

### 특징

- 자원 중심
- URI로 자원 식별
- 무상태성(Stateless)
- 통일된 인터페이스(Uniform Interface)

## 16-5. SOAP

SOAP는 Simple Object Access Protocol의 약자입니다.

XML 기반 메시지를 사용하여 구조화된 정보를 교환하는 프로토콜입니다.

### 특징

- XML 기반
- 메시지 형식과 처리 규칙 정의
- HTTP 등의 전송 프로토콜 활용 가능
- 웹 서비스 간 메시지 교환에 사용

# 17. 인터페이스 기술 비교

| 기술 | 핵심 개념 | 주요 특징 |
|---|---|---|
| AJAX | 비동기 화면 갱신 | 새로고침 없이 일부 화면 변경 |
| Fetch API | HTTP 요청 API | Promise 기반 |
| WebSocket | 실시간 양방향 통신 | 서버도 먼저 메시지 전송 가능 |
| GraphQL | API 쿼리 언어 | 필요한 필드 선택 |
| JSON-RPC | 원격 프로시저 호출 | JSON 메시지 기반 |
| REST | 아키텍처 스타일 | 자원 중심 |
| SOAP | 메시징 프로토콜 | XML 기반 |

## 헷갈리지 말아야 할 포인트

### AJAX vs Fetch API

- AJAX: 비동기적으로 데이터를 주고받아 화면을 갱신하는 기법
- Fetch API: HTTP 요청을 수행하는 JavaScript API

즉, Fetch API를 사용하여 AJAX 방식의 통신을 구현할 수 있습니다.

### REST vs GraphQL

- REST: 자원 중심의 아키텍처 스타일
- GraphQL: 필요한 데이터를 선택하여 요청하는 API 쿼리 언어

### HTTP vs WebSocket

- 일반적인 HTTP 사용 방식: 클라이언트 요청 → 서버 응답
- WebSocket: 연결을 유지하며 클라이언트와 서버가 양방향으로 메시지 교환

### JSON-RPC vs GraphQL

- JSON-RPC: 서버의 원격 메서드를 호출
- GraphQL: 필요한 데이터의 필드를 선택하여 요청

### SOAP vs REST

- SOAP: XML 기반 메시징 프로토콜
- REST: 자원 중심의 아키텍처 스타일
