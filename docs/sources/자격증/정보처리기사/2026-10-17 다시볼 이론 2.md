
# 정보처리기사 실기 - SOLID 원칙 및 UML 다이어그램

# 1. SOLID 객체지향 설계 원칙

## SOLID란?

SOLID는 객체지향 소프트웨어를 설계할 때 유지보수성과 확장성을 높이기 위한 5가지 설계 원칙입니다.

## SOLID 원칙의 장점

- **유지보수성 향상**: 코드 변경 시 영향 범위를 최소화
- **확장성 증대**: 새로운 기능 추가가 용이
- **재사용성 증대**: 모듈화된 코드를 다른 곳에서도 재사용 가능
- **테스트 용이성**: 책임이 분리되고 의존성이 줄어들어 단위 테스트 작성이 쉬워짐

## SOLID 5가지 원칙

| 약자 | 원칙 | 핵심 개념 |
|---|---|---|
| S | SRP (Single Responsibility Principle) | 단일 책임 원칙 |
| O | OCP (Open-Closed Principle) | 개방-폐쇄 원칙 |
| L | LSP (Liskov Substitution Principle) | 리스코프 치환 원칙 |
| I | ISP (Interface Segregation Principle) | 인터페이스 분리 원칙 |
| D | DIP (Dependency Inversion Principle) | 의존성 역전 원칙 |

---

# 2. 단일 책임 원칙 (SRP)

## Single Responsibility Principle

**하나의 클래스는 하나의 책임만 가져야 한다**는 원칙입니다.

클래스가 여러 개의 책임을 가지면 변경 사유가 많아지고, 한 기능의 변경이 다른 기능에 영향을 줄 수 있습니다.

### 예시

회원 정보를 관리하는 클래스가 다음 기능을 모두 수행한다고 가정합니다.

- 회원 정보 저장
- 이메일 전송
- 결제 처리

이렇게 서로 다른 책임이 하나의 클래스에 집중되어 있으면 수정이 어려워집니다.

SRP를 적용하면 다음과 같이 분리할 수 있습니다.

- UserService: 회원 관련 업무
- EmailService: 이메일 전송
- PaymentService: 결제 처리

### 핵심

- 하나의 클래스는 하나의 책임
- 변경 이유를 하나로 유지
- 기능 간 결합도 감소

※ 하나의 책임은 단순히 메서드가 하나라는 뜻이 아닙니다. 하나의 역할을 수행하기 위해 여러 메서드를 가질 수 있습니다.

# 3. 개방-폐쇄 원칙 (OCP)

## Open-Closed Principle

**소프트웨어 개체는 확장에 대해서는 열려 있고, 수정에 대해서는 닫혀 있어야 한다**는 원칙입니다.

새로운 기능을 추가할 때 기존 코드를 가능한 한 수정하지 않고 확장할 수 있도록 설계해야 합니다.

### 예시

결제 시스템에 다음 결제 수단이 있다고 가정합니다.

- 카드 결제
- 계좌이체

나중에 간편결제를 추가할 때 기존 결제 처리 코드를 계속 수정하는 것보다는 공통 결제 인터페이스를 구현하는 새로운 클래스를 추가하는 방식이 바람직합니다.

### 핵심

- 새로운 기능 추가 → 확장
- 기존 코드 변경 최소화
- 다형성과 추상화를 활용

※ 기존 코드를 절대 수정할 수 없다는 의미는 아닙니다.

# 4. 리스코프 치환 원칙 (LSP)

## Liskov Substitution Principle

**서브타입은 기반 타입을 대체해도 프로그램의 올바른 동작을 유지해야 한다**는 원칙입니다.

부모 클래스의 객체를 사용하는 곳에 자식 클래스 객체를 넣어도 기대하는 기능이 정상적으로 동작해야 합니다.

### 예시

동물(Animal) 클래스에 소리를 내는 기능이 있다고 가정합니다.

- Animal: makeSound()
- Dog: makeSound()
- Cat: makeSound()

Animal 타입을 사용하는 프로그램에서 Dog나 Cat 객체를 대신 사용해도 정상적으로 동작해야 합니다.

### 핵심

- 부모 타입을 자식 타입으로 대체 가능
- 상속 관계에서 동작의 일관성 유지
- 단순한 문법적 상속보다 올바른 동작이 중요

※ 부모 타입으로 형변환이 가능하다는 사실만으로 LSP를 만족하는 것은 아닙니다.

# 5. 인터페이스 분리 원칙 (ISP)

## Interface Segregation Principle

**클라이언트는 자신이 사용하지 않는 메서드에 의존하지 않아야 한다**는 원칙입니다.

너무 많은 기능을 가진 하나의 인터페이스보다 역할별로 분리된 인터페이스를 사용하는 것이 좋습니다.

### 예시

하나의 인터페이스에 다음 기능이 있다고 가정합니다.

```java
interface Machine {
    void print();
    void scan();
    void fax();
}
```

단순 프린터는 출력 기능만 필요하지만 스캔과 팩스 기능까지 구현해야 합니다.

ISP를 적용하면 다음과 같이 분리합니다.

```java
interface Printable {
    void print();
}

interface Scannable {
    void scan();
}

interface Faxable {
    void fax();
}
```

### 핵심

- 인터페이스를 역할별로 분리
- 불필요한 메서드 의존 방지
- 클라이언트에 필요한 기능만 제공

# 6. 의존성 역전 원칙 (DIP)

## Dependency Inversion Principle

**고수준 모듈은 저수준 모듈에 직접 의존하지 않고, 둘 다 추상화에 의존해야 한다**는 원칙입니다.

구체적인 구현 클래스보다는 인터페이스나 추상 클래스에 의존하도록 설계합니다.

### 고수준 모듈과 저수준 모듈

- 고수준 모듈: 핵심 비즈니스 로직을 처리
- 저수준 모듈: 데이터베이스 연결, 파일 저장 등 구체적인 기능 구현

### 예시

회원 서비스가 MySQL 저장 클래스에 직접 의존하면 데이터베이스 변경 시 회원 서비스 코드까지 수정해야 할 수 있습니다.

DIP를 적용하면 다음 구조를 사용할 수 있습니다.

```text
UserService
     ↓
UserRepository (인터페이스)
     ↑
MySQLRepository
```

회원 서비스는 MySQLRepository가 아니라 UserRepository 인터페이스에 의존합니다.

이렇게 하면 구현 클래스를 PostgreSQLRepository 등으로 교체하기가 쉬워집니다.

### 핵심

- 구체적인 구현보다 추상화에 의존
- 고수준 모듈과 저수준 모듈의 결합도 감소
- 구현체 변경에 유리

# 7. UML (Unified Modeling Language)

## UML이란?

UML은 Unified Modeling Language의 약자로, **통합 모델링 언어**를 의미합니다.

소프트웨어 시스템의 구조와 동작을 시각적으로 표현하기 위한 표준 모델링 언어입니다.

소프트웨어를 개발하는 과정은 건물을 짓는 것과 비슷합니다.

1. 요구사항 도출: 고객이 원하는 기능 파악
2. 요구사항 분석: 요구사항의 의미와 제약 확인
3. 명세화 및 설계: 시스템 구조와 동작을 구체적으로 표현
4. 검증: 요구사항을 올바르게 반영했는지 확인

UML은 특히 요구사항 분석과 시스템 설계 과정에서 활용됩니다.

### UML의 특징

- 시스템 구조와 동작을 시각적으로 표현
- 개발자 간 의사소통 지원
- 복잡한 시스템을 이해하기 쉽게 모델링
- 설계 내용의 문서화에 활용

## UML의 구성 요소

UML의 주요 구성 요소는 다음과 같습니다.

1. 사물 (Things)
2. 관계 (Relationships)
3. 다이어그램 (Diagrams)

### UML 사물의 종류

| 종류 | 설명 |
|---|---|
| 구조 사물 | 클래스, 인터페이스 등 시스템의 정적 구성 요소 |
| 행동 사물 | 상호작용, 상태 머신 등 시스템의 동작 |
| 그룹 사물 | 패키지처럼 모델 요소들을 그룹화 |
| 주해 사물 | 모델에 대한 설명이나 주석 |

# 8. UML 다이어그램의 종류

UML 다이어그램은 크게 두 가지로 구분합니다.

1. 구조 다이어그램 (정적 모델)
2. 행위 다이어그램 (동적 모델)

## 8-1. 구조 다이어그램

시스템의 정적인 구조를 표현하는 다이어그램입니다.

| 다이어그램 | 핵심 키워드 | 설명 |
|---|---|---|
| 클래스 | 속성, 메서드, 클래스 관계 | 클래스의 구조와 관계 표현 |
| 객체 | 인스턴스, 특정 시점 | 실제 객체와 객체 간 관계 표현 |
| 컴포넌트 | 컴포넌트, 의존 관계 | 시스템 구성 요소와 의존성 표현 |
| 배치(배포) | 물리적 요소, 배치 위치 | 노드와 실행 환경에 배포되는 요소 표현 |
| 복합체 구조 | 내부 구조, 협력 관계 | 클래스 또는 분류자의 내부 구성 표현 |
| 패키지 | 그룹화, 패키지 의존성 | 모델 요소를 그룹화하고 패키지 간 관계 표현 |

※ UML 표준에는 프로파일 다이어그램도 구조 다이어그램으로 분류됩니다.

## 8-2. 행위 다이어그램

시스템의 동적인 동작이나 처리 흐름을 표현하는 다이어그램입니다.

| 다이어그램 | 핵심 키워드 | 설명 |
|---|---|---|
| 유스케이스 | 사용자 관점 | 사용자와 시스템 기능의 상호작용 |
| 시퀀스 | 시간 흐름, 메시지 | 시간 순서에 따른 객체 간 메시지 교환 |
| 커뮤니케이션 | 객체 관계, 메시지 교환 | 객체들의 연결 관계와 메시지 교환 |
| 상태 | 상태 변화 | 하나의 객체가 겪는 상태 변화 |
| 활동 | 작업 흐름, 처리 로직 | 시스템 작업의 처리 흐름 |
| 타이밍 | 시간 제약 | 시간에 따른 객체 상태 변화 |

### 추가 행위 다이어그램

- 상호작용 개요 다이어그램: 여러 상호작용의 흐름 표현

※ 시퀀스, 커뮤니케이션, 타이밍, 상호작용 개요 다이어그램은 행위 다이어그램 중 상호작용 다이어그램으로도 분류됩니다.

### 행위 다이어그램 암기

**유시커 상활타**

- 유: 유스케이스
- 시: 시퀀스
- 커: 커뮤니케이션
- 상: 상태
- 활: 활동
- 타: 타이밍

시험에서는 이름뿐 아니라 설명에 포함된 핵심 키워드로 구분하는 것이 중요합니다.

# 9. 주요 UML 다이어그램 상세 설명

## 9-1. 클래스 다이어그램 (Class Diagram)

클래스의 속성, 메서드, 클래스 간 관계를 표현합니다.

### 주요 요소

- 클래스 이름
- 속성 (Attribute)
- 연산 또는 메서드 (Operation)
- 클래스 간 관계

### 클래스 표현 예시

```text
+--------------------+
|       Student      |
+--------------------+
| - name: String     |
| - age: int         |
+--------------------+
| + study(): void    |
| + getName(): String|
+--------------------+
```

### 접근 제어 기호

| 기호 | 의미 |
|---|---|
| + | public |
| - | private |
| # | protected |
| ~ | package (패키지 가시성) |

## 9-2. 객체 다이어그램 (Object Diagram)

클래스에서 생성된 실제 객체(인스턴스)와 객체 사이의 관계를 특정 시점에서 표현합니다.

### 구분

- 클래스 다이어그램: 설계된 클래스 구조
- 객체 다이어그램: 실제 생성된 객체의 모습

## 9-3. 컴포넌트 다이어그램 (Component Diagram)

시스템을 구성하는 컴포넌트와 그 사이의 의존 관계 및 인터페이스를 표현합니다.

### 핵심

- 컴포넌트
- 제공·요구 인터페이스
- 컴포넌트 간 의존성

## 9-4. 배치 다이어그램 (Deployment Diagram)

하드웨어 노드, 실행 환경, 소프트웨어 아티팩트 등이 실제 환경에 어떻게 배치되는지를 표현합니다.

### 예시

```text
사용자 PC
    ↓
웹 서버
    ↓
데이터베이스 서버
```

### 핵심

- 물리적 배치
- 하드웨어 노드
- 실행 환경
- 배포 관계

## 9-5. 복합체 구조 다이어그램 (Composite Structure Diagram)

클래스나 다른 분류자의 내부 구조와 내부 구성 요소들이 어떻게 협력하는지를 표현합니다.

클래스 다이어그램이 **무엇이 있는가?** 를 보여준다면, 복합체 구조 다이어그램은 **내부 구성 요소들이 어떻게 연결되어 협력하는가?** 를 보여줍니다.

### 주요 요소

- 내부 파트(Part)
- 포트(Port)
- 커넥터(Connector)
- 내부 협력 관계

### 핵심

- 내부 구조
- 구성 요소 간 연결
- 협력 관계

## 9-6. 패키지 다이어그램 (Package Diagram)

유스케이스, 클래스 등 여러 모델 요소를 패키지로 그룹화하고 패키지 간 의존 관계를 표현합니다.

### 특징

- 폴더 모양으로 표현
- 모델 요소 그룹화
- 패키지 간 의존성 표시
- 복잡한 시스템의 논리적 구조 정리

### 예시

```text
+----------------------+
| User                 |
|  +-------------------+
|  | UserController    |
|  | UserService       |
|  | UserRepository    |
|  +-------------------+
+----------------------+
```

※ 실제 UML 패키지 기호는 위쪽에 작은 탭이 있는 폴더 형태입니다.

# 10. UML 행위 다이어그램 상세 설명

## 10-1. 유스케이스 다이어그램 (Use Case Diagram)

사용자(Actor) 관점에서 시스템이 제공하는 기능과 사용자와의 상호작용을 표현합니다.

### 주요 요소

- 액터 (Actor)
- 유스케이스 (Use Case)
- 시스템 경계 (System Boundary)
- 관계 (Relationship)

### 예시

온라인 쇼핑몰에서 사용자가 수행하는 기능:

- 회원가입
- 로그인
- 상품 검색
- 주문
- 결제

### 핵심
사용자 관점, 시스템 기능, 상호작용

## 10-2. 시퀀스 다이어그램 (Sequence Diagram)

객체 간 메시지가 시간 순서에 따라 어떻게 전달되는지 표현합니다.

### 핵심
시간 흐름, 메시지 순서, 객체 간 호출

## 10-3. 커뮤니케이션 다이어그램 (Communication Diagram)

객체들이 어떤 관계로 연결되어 있으며 어떤 메시지를 교환하는지 표현합니다.

### 시퀀스와 차이점

- 시퀀스: 메시지의 시간 순서 강조
- 커뮤니케이션: 객체 간 연결 구조와 메시지 교환 강조

## 10-4. 상태 다이어그램 (State Machine Diagram)

객체가 특정 사건이나 조건에 따라 어떤 상태로 변화하는지 표현합니다.

### 예시

```text
대기 → 실행 중 → 완료
          ↓
         오류
```

### 핵심
상태, 이벤트, 전이

## 10-5. 활동 다이어그램 (Activity Diagram)

시스템이 수행하는 작업의 흐름과 처리 로직을 표현합니다.

### 예시

```text
시작
 ↓
로그인 정보 입력
 ↓
아이디·비밀번호 확인
 ↓
로그인 성공 여부 판단
 ├─ 성공 → 메인 페이지
 └─ 실패 → 오류 메시지
 ↓
종료
```

### 핵심
작업의 흐름, 처리 로직, 분기, 순서

## 10-6. 타이밍 다이어그램 (Timing Diagram)

시간의 흐름에 따라 객체나 시스템의 상태 또는 값이 어떻게 변화하는지 표현합니다.

### 핵심
시간 제약, 상태 변화, 시간 축

# 11. UML 클래스 다이어그램의 관계

클래스 다이어그램에서는 클래스 사이의 관계를 다양한 선과 화살표로 표현합니다.

## 관계 요약표

| 관계 | 기호 | 키워드 |
|---|---|---|
| 포함·복합 (Composition) | ◆── | 강한 전체-부분 관계, 속 찬 마름모 |
| 집합·집약 (Aggregation) | ◇── | 약한 전체-부분 관계, 독립적, 속 빈 마름모 |
| 연관 (Association) | ─── | 서로 관련, 구조적 연결, 실선 |
| 의존 (Dependency) | - - > | 사용 관계, 점선 화살표 |
| 일반화 (Generalization) | ──▷ | 상속, 일반적, 속 빈 삼각형 |
| 실체화 (Realization) | - -▷ | 인터페이스 구현, 속 빈 삼각형, 점선 |

### 시험에서 구분할 것

- Composition: 속이 채워진 마름모
- Aggregation: 속이 빈 마름모
- Association: 실선
- Dependency: 점선 화살표
- Generalization: 실선 + 속 빈 삼각형
- Realization: 점선 + 속 빈 삼각형

※ 연관 관계는 기본적으로 실선이며, 탐색 방향을 나타내는 화살표가 추가될 수 있습니다. 반드시 화살표가 있어야 하는 것은 아닙니다.

---

# 12. 포함·복합 관계 (Composition)

## 개념

전체와 부분 사이의 강한 소유 관계를 나타냅니다.

부분 객체의 생명주기가 전체 객체에 종속되는 관계입니다.

### 기호

◆──

속이 채워진 마름모를 사용합니다.

마름모는 전체를 나타내는 클래스 쪽에 표시합니다.

### 핵심 키워드

- 강한 관계
- 속 찬 마름모
- 전체와 부분
- 생명주기 종속

### 예시

집과 방

집은 여러 개의 방으로 구성될 수 있습니다.

개념적으로 집이 사라지면 그 집을 구성하는 방도 독립된 부분으로 유지되지 않는 관계입니다.

### 특징

- 전체와 부분의 강한 결합
- 부분의 생명주기가 전체에 종속
- 한 부분은 같은 시점에 여러 복합 객체에 동시에 속할 수 없음

※ 프로그래밍에서 전체 객체를 삭제하면 메모리상의 부분 객체도 항상 즉시 삭제된다는 의미는 아닙니다. UML의 모델링상 생명주기 관계를 뜻합니다.

---

# 13. 집합·집약 관계 (Aggregation)

## 개념

하나의 사물이 다른 사물의 부분이 되는 전체-부분 관계이지만, 부분 객체가 전체 객체와 독립적으로 존재할 수 있는 관계입니다.

### 기호

◇──

속이 비어 있는 마름모를 사용합니다.

마름모는 전체를 나타내는 클래스 쪽에 표시합니다.

### 핵심 키워드

- 포함 관계
- 독립적
- 속 빈 마름모
- 약한 전체-부분 관계

### 예시

학과와 학생

학과에는 여러 학생이 소속될 수 있습니다.

하지만 학과가 없어져도 학생이라는 객체 자체가 사라지는 것은 아닙니다.

### 특징

- 전체와 부분으로 구분
- 부분은 독립적으로 존재 가능
- 전체가 없어져도 부분이 유지될 수 있음

### 주의

문제에서 **포함**이라는 표현이 나온다고 무조건 Composition을 선택하면 안 됩니다.

- 강한 생명주기 종속 → Composition
- 서로 독립적 → Aggregation

특히 **서로 독립적인 관계**라는 표현이 나오면 Aggregation을 먼저 생각합니다.

---

# 14. 연관 관계 (Association)

## 개념

두 클래스 사이의 구조적 연결 관계를 표현합니다.

### 기호

───

실선으로 표시합니다.

필요한 경우 탐색 방향을 나타내기 위해 화살표를 사용할 수 있습니다.

### 핵심 키워드

- 서로 관련
- 연결 관계
- 지속적인 구조적 관계
- 실선

### 예시

야구팀과 투수 역할

야구팀과 투수 역할 사이의 연결을 연관 관계로 모델링할 수 있습니다.

여기서 투수는 반드시 특정 선수 한 명을 뜻하는 것은 아니며, 팀과 연결된 역할이라는 관점입니다.

### 특징

- 클래스 사이의 구조적 관계 표현
- 양방향 또는 단방향 탐색 가능
- 관계의 다중성 표현 가능

### 다중성 예시

| 기호 | 의미 |
|---|---|
| 1 | 정확히 1개 |
| 0..1 | 0개 또는 1개 |
| * | 0개 이상 |
| 1..* | 1개 이상 |
| 0..* | 0개 이상 |

※ 연관 관계도 상황에 따라 짧거나 길게 유지될 수 있으므로 지속 시간만으로 관계를 구분하지 않습니다.

---

# 15. 의존 관계 (Dependency)

## 개념

하나의 클래스가 다른 클래스를 사용하거나 참조하는 관계입니다.

한 클래스의 변경이 다른 클래스에 영향을 줄 수 있음을 나타냅니다.

### 기호

- - >

점선 화살표를 사용합니다.

화살표는 의존하는 대상 쪽을 향합니다.

### 핵심 키워드

- 사용 관계
- 점선 화살표
- 일시적인 사용 관계로 자주 설명
- 변경 영향

### 예시

개발자와 책

개발자가 학습을 위해 책을 사용하는 관계를 의존 관계로 나타낼 수 있습니다.

책은 개발자가 수행하는 특정 작업에서 사용되는 대상입니다.

### 프로그래밍 예시

```java
class Printer {
    void print() {
        System.out.println("출력");
    }
}

class Report {
    void createReport(Printer printer) {
        printer.print();
    }
}
```

Report 클래스의 메서드는 Printer 객체를 사용합니다.

이러한 사용 관계를 의존 관계로 표현할 수 있습니다.

### 특징

- 다른 클래스를 사용
- 메서드 매개변수나 지역 변수 등을 통한 사용 관계
- 점선 화살표

※ 의존 관계가 반드시 짧은 시간 동안만 유지되어야 하는 것은 아닙니다. 핵심은 한 요소가 다른 요소의 정의나 기능에 의존한다는 점입니다.

---

# 16. 일반화 관계 (Generalization)

## 개념

하나의 클래스가 다른 클래스보다 더 일반적인지 또는 구체적인지를 표현하는 관계입니다.

객체지향 프로그래밍의 상속 관계에 해당합니다.

### 기호

──▷

실선과 속이 빈 삼각형을 사용합니다.

삼각형은 부모 클래스(상위 클래스)를 향합니다.

### 핵심 키워드

- 상속
- 일반적
- 부모 클래스
- 자식 클래스
- IS-A 관계

### 예시

고양이는 동물이다.

```text
고양이 ──▷ 동물
```

- 동물: 상위 클래스
- 고양이: 하위 클래스

동물은 고양이보다 일반적인 개념입니다.

### Java 예시

```java
class Animal {
    void eat() {
        System.out.println("먹는다");
    }
}

class Cat extends Animal {
}
```

Cat은 Animal을 상속합니다.

### 특징

- 부모-자식 관계
- 상위 클래스의 속성과 메서드 상속 가능
- 다형성 구현에 활용

---

# 17. 실체화·실현 관계 (Realization)

## 개념

하나의 모델 요소가 다른 모델 요소에서 정의한 명세나 계약을 구현하는 관계입니다.

객체지향 프로그래밍에서는 대표적으로 클래스가 인터페이스를 구현하는 관계로 설명합니다.

### 기호

- -▷

점선과 속이 빈 삼각형을 사용합니다.

삼각형은 구현 대상인 인터페이스 쪽을 향합니다.

### 핵심 키워드

- 인터페이스
- 구현
- 약속
- 점선
- 속 빈 삼각형

### 예시

로봇청소기는 청소할 수 있다.

```text
로봇청소기 - -▷ 청소가능
```

청소가능은 청소 기능을 정의한 인터페이스입니다.

로봇청소기는 해당 인터페이스를 구현합니다.

### Java 예시

```java
interface Cleanable {
    void clean();
}

class RobotCleaner implements Cleanable {
    @Override
    public void clean() {
        System.out.println("청소 중");
    }
}
```

### 특징

- 인터페이스 구현
- 정의된 명세를 구체화
- 클래스와 인터페이스 관계에 자주 사용

---

# 18. UML 클래스 관계 비교

## 18-1. Composition vs Aggregation

| 구분 | Composition | Aggregation |
|---|---|---|
| 기호 | ◆ | ◇ |
| 마름모 | 속 찬 마름모 | 속 빈 마름모 |
| 관계 | 강한 전체-부분 | 약한 전체-부분 |
| 독립성 | 부분의 생명주기가 전체에 종속 | 부분이 독립적으로 존재 가능 |
| 예시 | 집과 방 | 학과와 학생 |

### 구분 방법

- 전체가 사라질 때 부분의 생명주기도 끝나는 관계 → Composition
- 전체가 사라져도 부분이 독립적으로 존재하는 관계 → Aggregation

## 18-2. Association vs Dependency

| 구분 | Association | Dependency |
|---|---|---|
| 기호 | 실선 | 점선 화살표 |
| 의미 | 구조적 연결 | 사용 또는 의존 |
| 특징 | 클래스 간 연관 | 한 요소가 다른 요소에 의존 |

### 구분 방법

- 클래스 간 구조적 관계 → Association
- 다른 클래스의 기능을 사용하거나 의존 → Dependency

## 18-3. Generalization vs Realization

| 구분 | Generalization | Realization |
|---|---|---|
| 선 | 실선 | 점선 |
| 화살표 | 속 빈 삼각형 | 속 빈 삼각형 |
| 의미 | 상속 | 명세 구현 |
| Java | extends | implements (대표적 예시) |

### 구분 방법

- 실선 + 속 빈 삼각형 → 일반화
- 점선 + 속 빈 삼각형 → 실체화

# 19. UML 기출·예상문제 1 - 구성 요소

## 문제

다음은 UML(Unified Modeling Language)에 대한 설명이다.

괄호 안에 들어갈 알맞은 용어를 쓰시오.

UML은 통합 모델링 언어로 구성 요소로는 사물, ( ① ), 다이어그램으로 이루어져 있으며, 구조 다이어그램 중 ( ② ) 다이어그램은 시스템에서 사용되는 객체 타입을 정의하고 속성과 연산을 표현한다.

( ③ )은/는 클래스와 같은 기타 모델 요소가 구현해야 하는 오퍼레이션 세트를 정의하는 모델 요소이다.

## 정답

① 관계 (Relationship)

② 클래스 (Class)

③ 인터페이스 (Interface)

## 해설

### ① 관계

UML의 기본 구성 요소는 사물, 관계, 다이어그램입니다.

### ② 클래스

클래스 다이어그램은 클래스의 속성, 메서드 및 클래스 사이의 관계를 표현합니다.

### ③ 인터페이스

인터페이스는 클래스 등이 구현해야 하는 연산의 명세를 정의합니다.

---

# 20. UML 기출·예상문제 2 - 패키지 다이어그램

## 문제

다음 설명에 해당하는 UML 다이어그램의 이름을 작성하시오.

1. 유스케이스나 클래스 등의 모델 요소들을 그룹화한다.
2. 패키지 간 의존 관계를 표현한다.
3. 폴더 형태의 기호를 사용한다.

## 정답

**패키지 다이어그램 (Package Diagram)**

## 해설

패키지 다이어그램은 모델 요소들을 패키지 단위로 그룹화하고, 패키지 사이의 의존 관계를 표현합니다.

### 핵심 키워드

- 유스케이스 또는 클래스 그룹화
- 패키지 간 의존성
- 폴더 모양

### 오답 구분

- 클래스 다이어그램: 속성, 메서드, 클래스 관계
- 컴포넌트 다이어그램: 컴포넌트 간 의존 관계
- 배치 다이어그램: 물리적인 배치 구조
- 패키지 다이어그램: 모델 요소 그룹화

---

# 21. UML 기출·예상문제 3 - 활동 다이어그램

## 문제

UML 다이어그램 중 시스템이 어떤 기능을 수행하는지에 대한 작업의 흐름과 처리 로직을 순서대로 표현하는 다이어그램으로, 객체의 처리 흐름을 표현할 때 사용되는 행위 다이어그램은 ( ) 다이어그램이다.

## 정답

**활동 다이어그램 (Activity Diagram)**

## 해설

활동 다이어그램은 시스템의 작업 흐름과 처리 순서 및 제어 흐름을 나타냅니다.

### 핵심 키워드

- 작업 흐름
- 처리 순서
- 처리 로직
- 조건 분기

### 오답 구분

- 시퀀스: 시간 순서에 따른 메시지 교환
- 상태: 객체의 상태 변화
- 활동: 작업과 처리 흐름
- 유스케이스: 사용자 관점의 기능

# 22. UML 기출·예상문제 4 - 집합 및 일반화 관계

## 문제

괄호 안의 설명에 맞는 UML 클래스 다이어그램 관계를 작성하시오.

1. 하나의 사물이 다른 사물에 포함되어 있는 관계이며, 전체와 부분으로 구분되고 클래스 간 서로 독립적인 관계는 ( ① ) 관계이다.

2. 하나의 사물이 다른 사물에 비해 일반적인지 구체적인지를 표현하는 관계는 ( ② ) 관계이다.

## 정답

① Aggregation (집합·집약 관계)

② Generalization (일반화 관계)

## 해설

### ① Aggregation

- 속이 빈 마름모 ◇
- 전체와 부분
- 독립적인 관계

문제에 '포함'이라는 표현이 있지만 **서로 독립적인 관계**라는 조건이 있으므로 Aggregation입니다.

### ② Generalization

- 속이 빈 삼각형
- 실선
- 부모와 자식
- 상속 관계

### 오답 분석

Composition은 전체-부분의 강한 관계이며 부분의 생명주기가 전체에 종속됩니다.

따라서 독립적인 관계라는 조건에 적합하지 않습니다.

# 23. UML 기출·예상문제 5 - 속 빈 삼각형 관계

## 문제

UML 클래스 다이어그램에서 속이 빈 삼각형 화살표를 사용하는 두 가지 관계를 모두 작성하시오.

## 정답

1. 일반화 (Generalization)
2. 실체화 (Realization)

## 해설

### 일반화

```text
자식 클래스 ───▷ 부모 클래스
```

- 실선
- 속 빈 삼각형
- 상속

### 실체화

```text
구현 클래스 - - -▷ 인터페이스
```

- 점선
- 속 빈 삼각형
- 인터페이스 구현

### 핵심

속이 빈 삼각형은 같지만 선의 종류가 다릅니다.

- 실선 → 일반화
- 점선 → 실체화

# 24. 추가 예상 문제

## 문제 1

하나의 클래스가 하나의 책임만 가져야 한다는 객체지향 설계 원칙은?

### 정답
SRP (단일 책임 원칙)

## 문제 2

소프트웨어 개체는 확장에 대해서 열려 있고 수정에 대해서 닫혀 있어야 한다는 원칙은?

### 정답
OCP (개방-폐쇄 원칙)

## 문제 3

자식 타입이 부모 타입을 대체하더라도 프로그램의 올바른 동작을 유지해야 한다는 원칙은?

### 정답
LSP (리스코프 치환 원칙)

## 문제 4

클라이언트가 사용하지 않는 메서드에 의존하지 않도록 인터페이스를 분리해야 한다는 원칙은?

### 정답
ISP (인터페이스 분리 원칙)

## 문제 5

고수준 모듈과 저수준 모듈이 모두 추상화에 의존하도록 설계하는 원칙은?

### 정답
DIP (의존성 역전 원칙)

## 문제 6

클래스의 속성, 메서드, 관계를 표현하는 UML 다이어그램은?

### 정답

## 문제 7

## 문제 8

시스템 구성 요소와 컴포넌트 사이의 의존 관계를 표현하는 다이어그램은?

## 문제 9

## 문제 10

클래스의 내부 구성 요소와 협력 관계를 표현하는 다이어그램은?

### 정답

## 문제 11

사용자 관점에서 시스템이 제공하는 기능을 표현하는 다이어그램은?

### 정답

## 문제 12

객체 사이에서 메시지가 전달되는 시간 순서를 표현하는 다이어그램은?

### 정답

## 문제 13

### 정답

# 25. 헷갈리지 말아야 할 포인트

## SOLID 원칙

| 원칙 | 핵심 |
|---|---|
| SRP | 하나의 책임 |
| OCP | 확장 가능, 기존 코드 수정 최소화 |
| LSP | 부모 타입을 자식 타입으로 대체 가능 |
| ISP | 사용하지 않는 인터페이스에 의존하지 않음 |
| DIP | 구체적인 구현보다 추상화에 의존 |

### OCP vs DIP

- OCP: 새로운 기능을 추가할 때 기존 코드 변경을 최소화
- DIP: 구체적인 구현 클래스가 아닌 추상화에 의존

서로 관련이 있지만 중점이 다릅니다.

### SRP vs ISP

- SRP: 클래스의 책임을 분리
- ISP: 인터페이스의 역할을 분리

## UML 구조 다이어그램

| 핵심 표현 | 정답 |
|---|---|
| 속성, 메서드 | 클래스 |
| 특정 시점, 인스턴스 | 객체 |
| 컴포넌트, 의존성 | 컴포넌트 |
| 물리적 배치, 노드 | 배치 |
| 내부 구조, 협력 | 복합체 구조 |
| 모델 요소 그룹화, 폴더 | 패키지 |

## UML 행위 다이어그램

| 핵심 표현 | 정답 |
|---|---|
| 사용자 관점, 시스템 기능 | 유스케이스 |
| 시간 흐름, 메시지 순서 | 시퀀스 |
| 객체 간 연결과 메시지 | 커뮤니케이션 |
| 상태 변화 | 상태 |
| 작업 흐름, 처리 로직 | 활동 |
| 시간 제약에 따른 변화 | 타이밍 |

## UML 클래스 관계

| 핵심 표현 | 정답 |
|---|---|
| 강한 전체-부분, 속 찬 마름모 | Composition |
| 독립적인 전체-부분, 속 빈 마름모 | Aggregation |
| 구조적 연결, 실선 | Association |
| 사용·의존, 점선 화살표 | Dependency |
| 상속, 실선 + 속 빈 삼각형 | Generalization |
| 인터페이스 구현, 점선 + 속 빈 삼각형 | Realization |

### 가장 헷갈리기 쉬운 3가지

**1. 포함이라는 단어만 보고 Composition을 선택하지 않기**

- 독립적이면 Aggregation
- 생명주기가 강하게 종속되면 Composition

**2. 속이 빈 삼각형은 두 가지 관계에서 사용**

- 실선이면 Generalization
- 점선이면 Realization

**3. 시퀀스와 활동 다이어그램 구분**

- 객체 사이의 메시지가 시간 순서대로 전달 → 시퀀스
- 작업의 처리 순서와 로직 → 활동

### 최종 구분

- 클래스 내부 구조와 협력 → 복합체 구조 다이어그램
- 클래스의 속성과 메서드 → 클래스 다이어그램
- 그룹화된 모델 요소와 패키지 의존성 → 패키지 다이어그램
- 시스템 기능을 사용자 관점에서 설명 → 유스케이스 다이어그램
- 객체의 상태 변화 → 상태 다이어그램
- 작업의 흐름과 처리 로직 → 활동 다이어그램
