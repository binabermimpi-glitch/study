# 1. 위험 감소(Risk Reduction) 🔥 빈출

## 문제

위험 처리 방식 중 백업, 이중화 장애대응 시스템, 방화벽, 보안 교육 등을 통해 위험 발생 가능성 및 피해 규모를 낮추는 방법

## 정답

**위험 감소(Risk Reduction)**

## 개념

위험 자체를 완전히 없애는 것이 아니라 보안 대책 등을 적용하여 **위험 발생 가능성이나 피해 규모를 낮추는 대응 방법**이다.

## 핵심

```text
발생 가능성 ↓
피해 규모 ↓
→ 위험 감소
```

## 같이 알아둘 위험 대응 방식

### 위험 회피(Avoidance)

위험이 발생할 수 있는 원인이나 활동 자체를 제거한다.

```text
위험한 기능 자체를 사용하지 않음
→ 위험 회피
```

### 위험 감소(Reduction)

보안 대책을 적용하여 위험의 발생 가능성이나 피해를 줄인다.

예:

* 백업
* 방화벽
* 시스템 이중화
* 보안 교육

### 위험 전가(Transfer)

위험에 따른 손실이나 책임을 다른 대상에게 이전한다.

예:

* 보험
* 외주 계약

### 위험 수용(Acceptance)

위험을 알고 있지만 비용 등을 고려하여 그대로 감수한다.

## 시험 구별

```text
백업 / 방화벽 / 이중화
→ 위험 감소

보험
→ 위험 전가

위험 요소 자체 제거
→ 위험 회피

위험을 알고 감수
→ 위험 수용
```

# 2. WSDL 🔥 빈출

## 문제

웹 서비스를 설명하기 위한 XML 표기법이다.
웹 서비스 요청 작성 방법을 클라이언트에 알려주며 웹 서비스 제공자가 제공하는 인터페이스를 설명한다.

## 정답

**WSDL(Web Services Description Language)**

## 개념

웹 서비스가 제공하는 기능, 호출 방법, 입력값과 출력값, 서비스 위치 등을 **XML 형식으로 설명하는 언어**이다.

쉽게 말하면:

```text
WSDL = 웹 서비스 사용 설명서
```

## 핵심 키워드

```text
웹 서비스
XML
인터페이스 설명
호출 방법
입력 / 출력
→ WSDL
```

## SOAP / WSDL / UDDI

```text
UDDI = 웹 서비스를 찾는다.
WSDL = 웹 서비스를 설명한다.
SOAP = 실제 메시지를 주고받는다.
```

### 암기

```text
UDDI = 찾기
WSDL = 설명서
SOAP = 통신
```

# 3. 시큐어 코딩(Secure Coding) 🔥 빈출

## 문제

개발자의 실수가 코드에 포함될 수 있는 보안 취약점을 최소화하는 보안 활동

## 정답

**시큐어 코딩(Secure Coding)**

## 개념

소프트웨어를 개발할 때부터 보안 취약점이 발생하지 않도록 **안전한 방법으로 소스 코드를 작성하는 활동**이다.

## 핵심

```text
개발 단계
+
보안 취약점 예방
+
안전한 코드 작성
→ 시큐어 코딩
```

## 대표적인 취약점

* SQL Injection
* XSS
* 입력값 검증 오류
* 중요 정보 노출
* 경로 조작
* 인증 및 권한 처리 오류

### Java와 연결

SQL Injection 방어 시 대표적으로:

```java
PreparedStatement
```

를 사용할 수 있다.

# 4. 시퀀스 다이어그램(Sequence Diagram) 🔥 빈출

## 문제

상호작용하는 시스템이나 객체들이 주고받는 메시지를 표현하는 다이어그램

## 정답

**시퀀스 다이어그램(Sequence Diagram)**

## 개념

객체들이 **시간의 흐름에 따라 어떤 메시지를 주고받는지** 표현하는 UML 다이어그램이다.

```text
객체 A        객체 B
  │              │
  │ ── 요청 ───→ │
  │              │
  │ ←─ 응답 ──── │
```

## 핵심 키워드

```text
객체
상호작용
메시지
시간 순서
→ 시퀀스 다이어그램
```

## UML 다이어그램 같이 구별

```text
클래스 다이어그램
→ 클래스의 구조와 관계

유스케이스 다이어그램
→ 사용자와 시스템 기능

시퀀스 다이어그램
→ 객체 간 메시지의 시간 순서

활동 다이어그램
→ 작업의 흐름
```

# 5. 성능(Performance) ⭐ 중요

## 문제

시스템 품질 속성 중 빠른 응답 시간을 의미하는 것

## 정답

**성능(Performance)**

## 개념

시스템이 사용자 요청을 얼마나 빠르고 효율적으로 처리하는지를 나타내는 품질 속성이다.

## 핵심

```text
빠른 응답 시간
빠른 처리
→ 성능
```

## 같이 알아둘 성능 측정 지표

### 처리량(Throughput)

일정 시간 동안 처리할 수 있는 작업의 양

### 응답 시간(Response Time)

요청한 시점부터 응답을 받을 때까지 걸리는 시간

### 경과 시간(Turnaround Time)

요청한 시점부터 전체 작업이 완료될 때까지의 시간

### 자원 사용률(Resource Usage)

CPU, 메모리, 네트워크 등의 사용량

# 6. 참 오라클(True Oracle) ⭐ 중요

## 문제

모든 테스트 케이스의 입력 값에 기대하는 결과를 제공하며 발생된 모든 오류를 검출할 수 있는 오라클

## 정답

**참 오라클(True Oracle)**

## 테스트 오라클

테스트를 수행했을 때 나온 결과가 올바른지 판단하기 위해 **기대되는 결과를 제공하는 방법**이다.

## 참 오라클

모든 입력값에 대해 정확한 예상 결과를 제공하여 모든 오류를 검출할 수 있다.

```text
모든 입력
+
정확한 기대 결과
→ 참 오라클
```

## 테스트 오라클 종류

### ① 참 오라클(True Oracle)

모든 테스트 입력에 대해 정확한 결과를 제공

### ② 샘플링 오라클(Sampling Oracle)

일부 테스트 케이스에 대해서만 결과를 제공

### ③ 휴리스틱 오라클(Heuristic Oracle)

일부 입력의 정확한 결과를 기반으로 나머지 결과를 추정

### ④ 일관성 검사 오라클(Consistent Oracle)

변경 전후의 결과가 서로 일관적인지를 확인

# 7. 세마포어(Semaphore) 🔥 빈출

## 문제

여러 스레드가 동시에 특정 공유 자원에 접근할 수 있는 허용 가능한 수를 제어하는 기술

## 정답

**세마포어(Semaphore)**

## 개념

공유 자원에 동시에 접근할 수 있는 **프로세스 또는 스레드의 개수를 제한하는 동기화 기법**이다.

예:

```text
Semaphore = 3
```

이라면 동시에 최대 3개까지 공유 자원에 접근할 수 있다.

## 핵심

```text
공유 자원
동시 접근
접근 가능 개수 제한
→ 세마포어
```

## Mutex와 비교

```text
Mutex
→ 한 번에 하나만 접근

Semaphore
→ 지정된 개수만큼 접근 가능
```

# 8. 베이스라인(Baseline) 🔥 빈출

## 문제

특정 시점에서 소프트웨어가 하나의 완전한 산출물로써 쓰여질 수 있는 상태의 집합

## 정답

**베이스라인(Baseline)**

## 개념

소프트웨어 개발 과정에서 **공식적으로 검토되고 승인되어 이후 변경의 기준이 되는 상태**이다.

쉽게 말하면:

```text
"여기까지는 공식적으로 확정"
```

된 상태이다.

예:

```text
요구사항 확정
→ 요구사항 Baseline

설계 확정
→ 설계 Baseline
```

베이스라인 이후 변경이 필요하면 일반적으로 형상 통제 절차를 거친다.

## 형상 관리 절차

```text
형상 식별
→ 형상 통제
→ 형상 감사
→ 형상 기록
```

# 9. 퍼사드 패턴(Facade Pattern) ⭐ 중요

## 문제

시스템을 단순하게 사용할 수 있도록 하는 인터페이스를 제공하여 시스템 간 느슨한 결합과 복잡성을 낮추는 디자인 패턴

## 정답

**퍼사드 패턴(Facade Pattern)**

## 개념

복잡한 여러 하위 시스템을 직접 사용하지 않고 **하나의 단순한 인터페이스를 통해 사용할 수 있도록 하는 구조 패턴**이다.

```text
사용자
   ↓
Facade
   ↓
시스템 A
시스템 B
시스템 C
```

## 핵심

```text
복잡한 시스템
↓
단순한 인터페이스 제공
↓
복잡성 감소
```

### 이름 기억

Facade는 건물의 **정면**이라는 의미이다.

건물 내부 구조를 몰라도 입구만 알면 사용할 수 있다는 느낌으로 기억하면 된다.

# 10. 결합도 순서 🔥🔥 매우 빈출

## 문제

결합도가 강한 것부터 순서대로 설명

## 정답

```text
내용
→ 공통
→ 외부
→ 제어
→ 스탬프
→ 자료
```

## 핵심

결합도는 **낮을수록 좋은 설계**이다.

```text
강함                                  약함
내용 → 공통 → 외부 → 제어 → 스탬프 → 자료
나쁨                                  좋음
```

## 결합도가 약한 순서

```text
자료
→ 스탬프
→ 제어
→ 외부
→ 공통
→ 내용
```

## 암기

```text
내공외제스자
```

```text
내 = 내용
공 = 공통
외 = 외부
제 = 제어
스 = 스탬프
자 = 자료
```

## 각각의 개념

### 내용 결합도(Content Coupling)

다른 모듈의 내부 데이터나 기능을 직접 사용

→ 가장 강한 결합도

### 공통 결합도(Common Coupling)

여러 모듈이 전역 변수 등의 공통 데이터를 사용

### 외부 결합도(External Coupling)

외부 데이터 형식, 장치 인터페이스, 프로토콜 등을 공유

### 제어 결합도(Control Coupling)

다른 모듈의 동작을 제어하는 값을 전달

### 스탬프 결합도(Stamp Coupling)

배열, 객체, 구조체 등 자료구조 전체를 전달

### 자료 결합도(Data Coupling)

단순 데이터 값만 전달

# 11. Kerberos(커버로스) ⭐ 중요

## 문제

1980년대 MIT Athena 프로젝트에서 개발된 대칭키 암호 프로토콜, 인증서버(AS, Authentication Server)로부터 TGT를 받아 티켓 부여 서버를 통해 인증을 받는 방식

## 정답

**Kerberos(커버로스)**

## 개념

대칭키 암호 방식을 이용하여 네트워크 사용자와 서비스를 인증하기 위한 **티켓 기반 인증 프로토콜**이다.

## 핵심 키워드

```text
MIT
Athena
대칭키
Ticket
TGT
KDC
→ Kerberos
```

## 구조

KDC(Key Distribution Center)는 일반적으로 다음으로 구성된다.

```text
KDC
├─ AS  : Authentication Server
└─ TGS : Ticket Granting Server
```

## 인증 흐름

```text
사용자
↓
AS에 인증 요청
↓
TGT 발급
↓
TGS에 TGT 전달
↓
서비스 티켓 발급
↓
서비스 이용
```

### 용어

**TGT**
Ticket Granting Ticket

서비스 티켓을 발급받기 위해 사용하는 티켓이다.

# 13. Fan-In ⭐ 중요

## 문제

어떤 모듈을 제어하는 다른 모듈의 수를 의미하는 용어

## 정답

**Fan-In**

## 개념

하나의 모듈을 **호출하거나 사용하는 상위 모듈의 개수**이다.

예:

```text
A ─┐
B ─┼──→ X
C ─┘
```

X를 호출하는 모듈이 A, B, C 세 개이므로

```text
Fan-In = 3
```

## Fan-Out도 같이 알아두기

Fan-Out은 하나의 모듈이 호출하거나 제어하는 **하위 모듈의 수**이다.

```text
       X
     ↙ ↓ ↘
    A  B  C
```

```text
Fan-Out = 3
```

## 암기

```text
Fan-In
→ 나에게 들어오는 것

Fan-Out
→ 내가 밖으로 호출하는 것
```

# 15. FP(Function Point) 🔥 빈출

## 문제

요구기능별로 가중치를 부여하는 상향식 비용 산정 모델로 요인별 가중치를 합산하여 총 기능의 점수를 계산하여 비용을 산정하는 방식이다.

## 정답

**FP(Function Point, 기능 점수)**

## 개념

소프트웨어가 제공하는 **기능의 수와 복잡도에 가중치를 적용하여 소프트웨어의 규모와 개발 비용을 산정하는 방법**이다.

## 핵심

```text
기능
+
가중치
=
기능 점수
```

## 문제 키워드

```text
요구 기능
가중치
기능 점수
비용 산정
→ FP
```

## 같이 알아둘 비용 산정 기법

```text
LOC
COCOMO
Putnam
FP
```

### LOC

소스 코드의 라인 수를 기준으로 비용을 산정

### COCOMO

소프트웨어 규모를 기반으로 개발 노력과 비용을 산정

### Putnam

소프트웨어 생명주기와 인력 분포를 기반으로 비용 산정

### FP

사용자가 요구하는 기능을 기준으로 가중치를 적용하여 산정

## FP 대표 기능

```text
EI  = External Input
EO  = External Output
EQ  = External Inquiry
ILF = Internal Logical File
EIF = External Interface File
```

처음에는 이것까지 전부 외우기보다

```text
기능에 가중치를 부여한다
→ FP
```

를 가장 먼저 기억하면 된다.

# 84. AJAX 🔥

## 문제

필요한 데이터만 웹 서버에 요청해서 받은 후 브라우저 전체 페이지를 새로고침하지 않고 일부 영역만 갱신하는 웹 개발 기법

## 정답

**AJAX(Asynchronous JavaScript and XML)**

## 개념

JavaScript를 이용하여 서버와 비동기적으로 데이터를 주고받고 페이지 전체를 다시 불러오지 않고 일부만 변경한다.
```text
비동기 요청
+
부분 화면 갱신
→ AJAX
```

### 중요

AJAX가 반드시 SOAP나 XML만 사용하는 것은 아니다.

현재는 JSON도 매우 많이 사용한다.
```text
AJAX
→ 비동기 통신 방식

JSON / XML
→ 주고받는 데이터 형식
```
