# 예외 처리

## 한 문장 설명

예외 처리는 프로그램 실행 중 문제가 생겼을 때 정상 흐름과 오류 처리 흐름을 분리하고, 필요한 경우 호출자에게 처리 책임을 전달하는 방법이다.

## 1. 예외 계층

```text
Throwable
 ├─ Error
 └─ Exception
      └─ RuntimeException
```

- `Error`: JVM이나 실행 환경의 심각한 문제로, 일반 애플리케이션이 보통 직접 복구하려 하지 않는다.
- `Exception`: 프로그램에서 처리하거나 호출자에게 전달할 수 있는 예외의 기반 타입이다.
- `RuntimeException`: 실행 중 발생하는 언체크드 예외의 기반 타입이다.

대표적인 RuntimeException에는 `NullPointerException`, `ArithmeticException`, `NumberFormatException`, `IllegalArgumentException` 등이 있다.

> `Exception`을 직접 상속한 예외는 체크드 예외, `RuntimeException`을 상속한 예외는 언체크드 예외다. 체크드 예외는 컴파일러가 처리 또는 `throws` 선언을 요구한다.

## 2. try-catch-finally

```java
try {
    // 예외가 발생할 수 있는 코드
} catch (ExceptionType e) {
    // 발생한 예외 처리
} finally {
    // 마무리 코드
}
```

```text
try 실행
→ 예외 발생
→ 타입이 맞는 catch 실행
→ finally 실행
```

`finally`는 일반적으로 예외 발생 여부와 관계없이 실행된다. 다만 JVM 프로세스가 강제 종료되는 등의 특수 상황까지 무조건 실행된다고 단정하지 않는다. 파일·DB 연결처럼 닫아야 하는 자원은 가능하면 try-with-resources를 사용한다.

## 3. 여러 catch의 순서

여러 catch는 위에서부터 검사하며 처음으로 타입이 맞는 하나만 실행한다.

```java
try {
    Integer.parseInt("abc");
} catch (NumberFormatException e) {
    System.out.println("숫자 형식 오류");
} catch (RuntimeException e) {
    System.out.println("실행 예외");
} catch (Exception e) {
    System.out.println("일반 예외");
}
```

자식 예외를 먼저, 부모 예외를 나중에 작성한다. 부모 catch를 먼저 두면 뒤의 자식 catch가 도달 불가능해 컴파일 오류가 발생한다.

## 4. throw와 throws

```java
throw new ScoreException("점수 오류");
```

`throw`는 예외 객체를 실제로 발생시킨다.

```java
void checkScore(int score) throws ScoreException {
}
```

`throws`는 이 메서드에서 해당 예외가 호출자에게 전달될 수 있음을 선언한다. `throws`를 적었다고 예외가 무조건 발생하는 것은 아니다.

```text
throw  → 지금 예외를 발생시킨다
throws → 발생 가능한 예외와 전파 가능성을 선언한다
```

## 5. 사용자 정의 예외

```java
class ScoreException extends Exception {
    public ScoreException(String message) {
        super(message);
    }
}
```

업무 의미가 드러나는 새로운 예외 타입을 만들 수 있다. `super(message)`는 부모인 Throwable 영역에 메시지를 전달하며, catch에서 받은 예외 객체의 `getMessage()`로 이를 읽는다.

```text
new ScoreException("점수 오류")
→ 생성자의 message로 전달
→ super(message)
→ Throwable에 메시지 저장
→ e.getMessage()로 조회
```

## 6. 예외 전파와 재던지기

```java
try {
    service.submit();
} catch (RetryLimitException e) {
    System.out.println("재시도 제한");
    throw e;
} finally {
    System.out.println("마무리");
}
```

`throw e`는 새 예외를 만드는 것이 아니라 현재 잡은 같은 예외 객체를 호출자에게 다시 던진다. 이를 재던지기라고 한다.

```text
예외 발생
→ 현재 메서드의 catch 실행
→ throw e로 재던지기
→ finally 실행
→ 현재 메서드의 나머지 일반 코드는 건너뜀
→ 호출자의 알맞은 catch가 처리
```

자식 예외 객체는 부모 예외 타입의 catch에서도 받을 수 있다.

```text
RetryLimitException
        ↓
QuizException
        ↓
LearningException
```

RetryLimitException에 정확히 일치하는 catch가 없어도 `catch (QuizException e)`가 받을 수 있다.

## 7. 전체 예제의 실행 흐름

```java
class LearningException extends Exception {
    LearningException(String message) {
        super(message);
    }
}

class QuizException extends LearningException {
    QuizException(String message) {
        super(message);
    }
}

class RetryLimitException extends QuizException {
    RetryLimitException(String message) {
        super(message);
    }
}

class QuizService {
    static void submit(int score, int retry) throws LearningException {
        try {
            if (score < 0 || score > 100) {
                throw new QuizException("점수 범위 오류");
            }
            if (retry >= 3) {
                throw new RetryLimitException("재응시 횟수 초과");
            }
            System.out.println("A");
        } catch (RetryLimitException e) {
            System.out.println("B");
            throw e;
        } finally {
            System.out.println("C");
        }
        System.out.println("D");
    }
}

public class Main {
    public static void main(String[] args) {
        try {
            QuizService.submit(80, 3);
            System.out.println("E");
        } catch (QuizException e) {
            System.out.println("F");
            System.out.println(e.getMessage());
        } catch (LearningException e) {
            System.out.println("G");
        }

        System.out.println("H");
    }
}
```

`submit(80, 3)`을 호출하면 출력 흐름은 다음과 같다.

```text
submit(80, 3)
→ score 정상
→ retry >= 3
→ RetryLimitException 발생
→ catch (RetryLimitException e)
→ B 출력
→ throw e로 같은 예외 객체를 호출자에게 재전달
→ finally에서 C 출력
→ D는 실행하지 않음
→ main으로 예외 전달
→ RetryLimitException은 QuizException의 자식
→ catch (QuizException e)
→ F 출력
→ e.getMessage()로 "재응시 횟수 초과" 출력
→ H 출력
```

```text
B
C
F
재응시 횟수 초과
H
```

`D`는 재던진 예외 때문에 실행되지 않는다. `finally`의 `C`는 호출자에게 예외가 전달되기 전에 실행된다.

`E` 역시 `QuizService.submit(80, 3)` 호출이 정상 완료되지 않고 예외가 전달되므로 실행되지 않는다. `G`는 그보다 먼저 있는 `catch (QuizException e)`가 예외를 처리했으므로 실행되지 않는다.

## 문제를 읽을 때 확인할 순서

1. 어떤 코드에서 어떤 예외 객체가 발생하는가?
2. 현재 메서드에 타입이 맞는 catch가 있는가?
3. 잡은 예외를 처리하고 끝내는가, 다시 던지는가?
4. finally에서 무엇이 실행되는가?
5. 예외가 남아 있다면 호출자의 어느 catch가 받는가?
6. 예외로 흐름이 이동해 실행되지 않는 일반 코드는 무엇인가?

## 흔한 실수

- `throw`와 `throws`를 같은 의미로 생각한다.
- 부모 예외 catch를 자식 예외 catch보다 먼저 작성한다.
- `throws` 선언만으로 예외가 실제 발생한다고 생각한다.
- `throw e`가 새로운 예외 객체를 만든다고 생각한다.
- 예외를 재던진 뒤 현재 메서드의 아래 코드도 계속 실행된다고 생각한다.
- `finally`를 모든 상황에서 반드시 실행된다고 지나치게 단정한다.

## 실무에서는 어떻게 쓰이나

Spring 백엔드에서는 잘못된 요청, 찾을 수 없는 데이터, 권한 부족 같은 상황을 의미 있는 예외로 표현하고 공통 예외 처리기로 HTTP 응답에 변환한다. 예외를 무조건 잡아 숨기기보다 현재 계층이 처리할 책임이 있는지 판단해야 한다.
