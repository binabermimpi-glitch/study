## 04-2 TCP와 UDP

## 1. TCP와 UDP의 기본 차이

TCP와 UDP는 전송 계층에서 사용하는 대표적인 프로토콜이다.

| 구분 | TCP | UDP |
|---|---|---|
| 전체 이름 | Transmission Control Protocol | User Datagram Protocol |
| 연결 방식 | 연결형 | 비연결형 |
| 신뢰성 | 신뢰성 있는 전송 제공 | 신뢰성을 기본적으로 보장하지 않음 |
| 순서 보장 | 보장함 | 보장하지 않음 |
| 재전송 | 지원 | 기본적으로 지원하지 않음 |
| 흐름 제어 | 지원 | 지원하지 않음 |
| 혼잡 제어 | 지원 | 지원하지 않음 |
| 상태 관리 | 상태 유지 | 상태를 유지하지 않음 |
| 속도 | 상대적으로 느림 | 상대적으로 빠름 |
| 헤더 크기 | 기본 20바이트 이상 | 8바이트 |
| 데이터 단위 | 세그먼트 | 데이터그램 |
| 주요 사용 | 웹, 파일 전송, 이메일, 원격 접속 | 영상·음성 스트리밍, 인터넷 전화, DNS |

# 04-2-1 TCP

## 2. TCP의 특징

TCP는 연결형 통신과 신뢰성 있는 통신을 제공하는 전송 계층 프로토콜이다.

TCP의 주요 특징은 다음과 같다.

- 통신 전에 연결을 수립한다.
- 통신이 끝나면 연결을 종료한다.
- 송신한 데이터의 도착 여부를 확인한다.
- 손실된 데이터를 재전송한다.
- 데이터의 순서를 보장한다.
- 흐름 제어를 제공한다.
- 혼잡 제어를 제공한다.
- 현재 연결 상태를 유지한다.

TCP는 통신 상태를 유지하고 활용하기 때문에 **스테이트풀 프로토콜(Stateful Protocol)**이라고 한다.

---

## 3. TCP 통신 단계

TCP 통신은 크게 세 단계로 이루어진다.

| 단계 | 과정 | 설명 |
|---:|---|---|
| 1 | 연결 수립 | 송신자와 수신자가 통신 준비 |
| 2 | 데이터 송수신 | 세그먼트를 주고받음 |
| 3 | 연결 종료 | 연결을 안전하게 해제 |

전체 흐름:

`연결 수립 → 데이터 송수신 → 연결 종료`

TCP 연결 수립에는 일반적으로 **3-way handshake**가 사용되고, 연결 종료에는 일반적으로 **4-way handshake**가 사용된다.

---

## 4. MSS

MSS는 **Maximum Segment Size**의 약자이다.

TCP 세그먼트 하나가 전송할 수 있는 **최대 TCP 페이로드 크기**를 의미한다.

### MSS에 포함되는 것

| 구성 요소 | MSS 포함 여부 |
|---|---|
| TCP 페이로드 | 포함 |
| TCP 헤더 | 포함하지 않음 |
| IP 헤더 | 포함하지 않음 |
| 이더넷 헤더 | 포함하지 않음 |
| FCS | 포함하지 않음 |

### MTU와 MSS의 차이

| 구분 | 의미 |
|---|---|
| MTU | IP 패킷 전체가 한 번에 전송될 수 있는 최대 크기 |
| MSS | TCP 헤더를 제외한 TCP 데이터의 최대 크기 |

구조:

| 이더넷 헤더 | IP 헤더 | TCP 헤더 | TCP 페이로드 | FCS |
|---|---|---|---|---|
| MTU에 미포함 | MTU에 포함 | MTU에 포함 | MTU에 포함 | MTU에 미포함 |
| MSS에 미포함 | MSS에 미포함 | MSS에 미포함 | MSS에 포함 | MSS에 미포함 |

일반적인 IPv4 TCP 환경에서 옵션이 없다고 가정하면 다음과 같이 계산한다.

`MSS = MTU - IP 헤더 크기 - TCP 헤더 크기`

이더넷 MTU가 1500바이트인 경우:

`1500 - IPv4 헤더 20 - TCP 헤더 20 = 1460바이트`

따라서 일반적인 MSS는 다음과 같다.

`MSS = 1460바이트`

> IP 헤더나 TCP 헤더에 옵션이 추가되면 헤더 크기가 커지므로 실제 MSS는 더 작아질 수 있다.

### MTU와 MSS 암기

> MTU는 IP 헤더까지 포함하지만, MSS는 TCP 페이로드만 의미한다.

## 5. TCP 세그먼트 구조

TCP에서 송수신하는 데이터 단위를 **TCP 세그먼트**라고 한다.

TCP 세그먼트는 TCP 헤더와 페이로드로 구성된다.

| TCP 헤더 | TCP 페이로드 |
|---|---|
| 포트, 순서 번호, ACK 번호, 플래그 등 | 실제 전송 데이터 |

### TCP 헤더의 주요 필드

| 필드 | 주요 역할 |
|---|---|
| 송신지 포트 | 데이터를 보낸 프로세스 식별 |
| 수신지 포트 | 데이터를 받을 프로세스 식별 |
| 순서 번호 | 세그먼트 데이터의 순서 표시 |
| 확인 응답 번호 | 다음에 받을 것으로 기대하는 순서 번호 |
| 데이터 오프셋 | TCP 헤더의 길이 표시 |
| 제어 비트 | 세그먼트의 성격과 목적 표시 |
| 윈도우 | 한 번에 수신 가능한 데이터 크기 표시 |
| 체크섬 | TCP 헤더와 데이터의 오류 검출 |
| 긴급 포인터 | 긴급 데이터의 위치 표시 |
| 옵션 | MSS 등 추가 정보 표시 |
| 페이로드 | 실제 전송하려는 데이터 |

### TCP 헤더 구조

| 비트 범위 | 필드 |
|---|---|
| 0~15 | 송신지 포트 |
| 16~31 | 수신지 포트 |
| 다음 32비트 | 순서 번호 |
| 다음 32비트 | 확인 응답 번호 |
| 다음 영역 | 데이터 오프셋, 예약, 제어 비트, 윈도우 |
| 다음 영역 | 체크섬, 긴급 포인터 |
| 가변 영역 | 옵션 |
| 나머지 | TCP 페이로드 |

## 6. 송신지 포트와 수신지 포트

### 송신지 포트

TCP 세그먼트를 보낸 애플리케이션 프로세스를 식별한다.

### 수신지 포트

TCP 세그먼트를 받을 애플리케이션 프로세스를 식별한다.

예를 들어 웹 브라우저가 HTTP 서버로 요청한다면 다음과 같이 설정될 수 있다.

| 구분 | 포트 |
|---|---:|
| 클라이언트 송신지 포트 | 55000 |
| HTTP 서버 수신지 포트 | 80 |

서버가 응답할 때는 반대로 설정된다.

| 구분 | 포트 |
|---|---:|
| HTTP 서버 송신지 포트 | 80 |
| 클라이언트 수신지 포트 | 55000 |

## 7. 순서 번호

순서 번호(Sequence Number)는 TCP 세그먼트 데이터의 순서를 나타내는 번호이다.

정확히는 다음을 의미한다.

> 현재 TCP 세그먼트의 페이로드에서 첫 번째 바이트에 부여된 번호

TCP는 데이터를 바이트 단위로 번호를 매겨 관리한다.

따라서 다음 세그먼트의 순서 번호는 일반적으로 다음과 같이 계산한다.

`다음 순서 번호 = 현재 순서 번호 + 전송한 데이터의 바이트 수`

### 초기 순서 번호

연결을 시작할 때 사용하는 최초의 순서 번호를 **ISN(Initial Sequence Number)**이라고 한다.

- 연결마다 초기 순서 번호가 선택된다.
- 일반적으로 예측하기 어려운 값으로 정해진다.
- 양쪽 호스트는 서로 다른 초기 순서 번호를 사용한다.

### 순서 번호 계산 예제

초기 순서 번호가 100이고, 다음과 같이 데이터를 전송한다고 가정한다.

| 세그먼트 | 데이터 크기 | 순서 번호 | 계산 |
|---|---:|---:|---|
| 세그먼트 A | 500바이트 | 100 | 초기 순서 번호 |
| 세그먼트 B | 500바이트 | 600 | `100+500` |
| 세그먼트 C | 500바이트 | 1100 | `600+500` |
| 세그먼트 D | 400바이트 | 1600 | `1100+500` |

세그먼트 D까지 정상적으로 수신한 다음 기대 순서 번호는 다음과 같다.

`1600+400=2000`

### 순서 번호 흐름

| 세그먼트 A | 세그먼트 B | 세그먼트 C | 세그먼트 D |
|---|---|---|---|
| 500바이트 | 500바이트 | 500바이트 | 400바이트 |
| 순서 번호 100 | 순서 번호 600 | 순서 번호 1100 | 순서 번호 1600 |

> 순서 번호는 세그먼트의 개수를 세는 번호가 아니라, 데이터의 바이트 위치를 나타내는 번호이다.

## 8. 확인 응답 번호

확인 응답 번호(Acknowledgment Number)는 상대방에게서 다음으로 받기를 기대하는 순서 번호이다.

다음과 같이 계산할 수 있다.

`확인 응답 번호 = 수신한 세그먼트의 순서 번호 + 정상적으로 수신한 데이터 크기`

예를 들어 다음 세그먼트를 수신했다고 가정한다.

- 순서 번호: 100
- 데이터 크기: 500바이트

다음으로 기대하는 순서 번호:

`100+500=600`

따라서 확인 응답 번호는 600이 된다.

| 수신한 세그먼트 순서 번호 | 수신한 데이터 크기 | 확인 응답 번호 |
|---:|---:|---:|
| 100 | 500바이트 | 600 |
| 600 | 500바이트 | 1100 |
| 1100 | 500바이트 | 1600 |
| 1600 | 400바이트 | 2000 |

### 중요한 주의점

확인 응답 번호는 항상 단순히 `수신한 순서 번호+1`이 아니다.

데이터를 수신했다면 다음과 같이 계산한다.

`ACK 번호 = 순서 번호 + 수신한 데이터의 바이트 수`

다만 SYN과 FIN은 데이터가 없어도 순서 번호를 1만큼 소비한다.

따라서 SYN 또는 FIN에 대한 확인 응답 번호는 일반적으로 다음과 같다.

`ACK 번호 = 상대방의 순서 번호+1`

### ACK 플래그

확인 응답 번호 필드가 유효하다는 것을 나타내려면 ACK 플래그를 1로 설정한다.

## 9. 제어 비트

제어 비트 또는 플래그 비트는 현재 TCP 세그먼트의 성격과 목적을 나타낸다.

대표적인 제어 비트는 다음과 같다.

| 제어 비트 | 의미 |
|---|---|
| CWR | 혼잡 윈도우를 감소시켰음을 알림 |
| ECE | 네트워크 혼잡 상태를 알림 |
| URG | 긴급 포인터 필드가 유효함 |
| ACK | 확인 응답 번호가 유효함 |
| PSH | 데이터를 응용 프로그램에 빠르게 전달하도록 요청 |
| RST | 연결을 강제로 초기화 |
| SYN | TCP 연결 수립과 순서 번호 동기화 |
| FIN | TCP 연결 종료 요청 |

### 시험에서 중요한 플래그

| 플래그 | 핵심 역할 |
|---|---|
| ACK | 세그먼트 수신 확인 |
| SYN | 연결 수립 |
| FIN | 정상적인 연결 종료 |
| RST | 연결의 강제 종료·초기화 |

---

## 10. 윈도우

윈도우(Window) 필드에는 수신자가 한 번에 수신할 수 있는 데이터의 크기가 명시된다.

이를 **수신 윈도우(Receive Window)**라고 한다.

수신자는 윈도우 값을 이용하여 송신자에게 다음과 같이 알린다.

> 확인 응답을 기다리지 않고 현재 추가로 받을 수 있는 데이터의 양

윈도우는 TCP의 **흐름 제어**에 사용된다.

수신자가 처리할 수 있는 양보다 송신자가 지나치게 많은 데이터를 보내는 것을 방지한다.

# TCP 연결 수립

## 11. 3-way handshake

TCP는 데이터를 송수신하기 전에 연결을 수립한다.

TCP의 대표적인 연결 수립 과정을 **3-way handshake**라고 한다.

세 개의 세그먼트를 주고받기 때문에 3-way handshake라고 한다.

### 기본 흐름

| 순서 | 송수신 방향 | 세그먼트 | 주요 정보 | 의미 |
|---:|---|---|---|---|
| 1 | A → B | SYN | A의 ISN, SYN=1 | 연결을 시작합니다 |
| 2 | B → A | SYN+ACK | B의 ISN, A에 대한 ACK, SYN=1, ACK=1 | 확인했습니다. 저도 연결을 시작합니다 |
| 3 | A → B | ACK | B에 대한 ACK, ACK=1 | 확인했습니다 |

### 연결 수립 흐름도

| 호스트 A | 방향 | 호스트 B |
|---|---|---|
| SYN 전송 | `A → B` | SYN 수신 |
| SYN+ACK 수신 | `A ← B` | SYN+ACK 전송 |
| ACK 전송 | `A → B` | ACK 수신 |
| 연결 확립 |  | 연결 확립 |

---

## 12. 3-way handshake 순서 번호 계산

다음과 같이 초기 순서 번호를 가정한다.

- 호스트 A의 ISN: 1000
- 호스트 B의 ISN: 5000

### 첫 번째 단계

호스트 A가 SYN 세그먼트를 전송한다.

| 항목 | 값 |
|---|---:|
| SYN | 1 |
| 순서 번호 | 1000 |

SYN은 순서 번호를 1만큼 소비한다.

따라서 호스트 B는 다음 번호인 1001을 기대한다.

### 두 번째 단계

호스트 B가 SYN+ACK 세그먼트를 전송한다.

| 항목 | 값 |
|---|---:|
| SYN | 1 |
| ACK | 1 |
| 순서 번호 | 5000 |
| 확인 응답 번호 | 1001 |

의미:

- 호스트 A의 SYN을 확인했다.
- 다음에는 호스트 A의 1001번부터 받겠다.
- 호스트 B의 초기 순서 번호는 5000이다.

### 세 번째 단계

호스트 A가 ACK 세그먼트를 전송한다.

| 항목 | 값 |
|---|---:|
| ACK | 1 |
| 순서 번호 | 1001 |
| 확인 응답 번호 | 5001 |

호스트 B가 보낸 SYN도 순서 번호를 1만큼 소비하므로 확인 응답 번호는 5001이 된다.

### 전체 정리

| 순서 | 방향 | 플래그 | 순서 번호 | ACK 번호 |
|---:|---|---|---:|---:|
| 1 | A → B | SYN | 1000 | 없음 |
| 2 | B → A | SYN+ACK | 5000 | 1001 |
| 3 | A → B | ACK | 1001 | 5001 |

> SYN과 FIN은 데이터가 없어도 순서 번호를 1만큼 소비한다.

## 13. 액티브 오픈과 패시브 오픈

### 액티브 오픈

TCP 연결을 먼저 시작하는 호스트의 연결 수립 과정이다.

일반적으로 클라이언트가 액티브 오픈을 수행한다.

- SYN을 먼저 전송한다.
- SYN-SENT 상태로 전환한다.

### 패시브 오픈

상대방의 연결 요청을 기다리고 수락하는 호스트의 연결 수립 과정이다.

일반적으로 서버가 패시브 오픈을 수행한다.

- LISTEN 상태에서 SYN을 기다린다.
- SYN을 받으면 SYN+ACK를 전송한다.

| 구분 | 일반적인 주체 | 역할 |
|---|---|---|
| 액티브 오픈 | 클라이언트 | 연결 요청 시작 |
| 패시브 오픈 | 서버 | 연결 요청 대기 및 수락 |

---

# TCP 연결 종료

## 14. 4-way handshake

TCP 연결 종료 과정에서는 일반적으로 양쪽 호스트가 각각 FIN과 ACK를 주고받는다.

TCP는 양방향 통신이므로 한쪽 방향의 데이터 전송을 종료한 뒤 다른 방향도 별도로 종료한다.

따라서 일반적으로 네 단계로 연결이 종료된다.

### 연결 종료 과정

| 순서 | 송수신 방향 | 세그먼트 | 주요 정보 | 의미 |
|---:|---|---|---|---|
| 1 | A → B | FIN | FIN=1 | 제 쪽에서는 더 보낼 데이터가 없습니다 |
| 2 | B → A | ACK | ACK=1 | 종료 요청을 확인했습니다 |
| 3 | B → A | FIN | FIN=1 | 저도 더 보낼 데이터가 없습니다 |
| 4 | A → B | ACK | ACK=1 | 종료 요청을 확인했습니다 |

### 연결 종료 흐름도

| 호스트 A | 방향 | 호스트 B |
|---|---|---|
| FIN 전송 | `A → B` | FIN 수신 |
| ACK 수신 | `A ← B` | ACK 전송 |
| FIN 수신 | `A ← B` | FIN 전송 |
| ACK 전송 | `A → B` | ACK 수신 |
| 일정 시간 대기 |  | 연결 종료 |
| 연결 종료 |  |  |

> ACK와 FIN이 하나의 세그먼트에 함께 포함되는 경우에는 종료 과정이 세 개의 세그먼트로 진행될 수도 있다.

---

## 15. 액티브 클로즈와 패시브 클로즈

### 액티브 클로즈

연결 종료를 먼저 시작한 호스트의 종료 과정이다.

- FIN을 먼저 전송한다.
- 일반적으로 마지막 ACK를 전송한 후 TIME-WAIT 상태에 들어간다.

### 패시브 클로즈

상대방의 종료 요청을 받은 호스트의 종료 과정이다.

- 상대방의 FIN을 수신한다.
- ACK를 전송한다.
- 자신도 종료할 준비가 끝나면 FIN을 전송한다.

| 구분 | 의미 |
|---|---|
| 액티브 클로즈 | 연결 종료를 먼저 요청 |
| 패시브 클로즈 | 상대방의 종료 요청을 수락 |

---

# TCP 상태

## 16. TCP 상태란?

TCP 상태는 현재 TCP 연결이 어떤 통신 과정에 있는지를 나타내는 정보이다.

TCP는 연결 수립, 데이터 송수신, 연결 종료 과정의 상태를 유지한다.

따라서 TCP를 스테이트풀 프로토콜이라고 한다.

TCP 상태는 크게 다음과 같이 구분할 수 있다.

1. 연결이 수립되지 않은 상태
2. 연결 수립 과정의 상태
3. 연결이 확립된 상태
4. 연결 종료 과정의 상태

---

## 17. 연결이 수립되지 않은 상태

### CLOSED

아무런 TCP 연결이 없는 상태이다.

- 연결을 시작하기 전의 상태
- 연결이 완전히 종료된 상태

### LISTEN

연결 요청을 기다리는 상태이다.

- 서버가 주로 사용하는 상태
- 패시브 오픈 호스트의 상태
- 클라이언트의 SYN 세그먼트를 기다린다.

서버가 LISTEN 상태에서 SYN을 수신하면 3-way handshake가 시작된다.

---

## 18. 연결 수립 과정의 상태

### SYN-SENT

액티브 오픈 호스트가 SYN을 전송한 뒤 SYN+ACK를 기다리는 상태이다.

일반적으로 클라이언트에서 볼 수 있다.

### SYN-RECEIVED

패시브 오픈 호스트가 SYN을 받은 후 SYN+ACK를 전송하고, 마지막 ACK를 기다리는 상태이다.

일반적으로 서버에서 볼 수 있다.

### ESTABLISHED

TCP 연결이 정상적으로 수립된 상태이다.

- 데이터 송수신 가능
- 클라이언트와 서버 모두 ESTABLISHED 상태가 됨

### 연결 수립 상태 변화

#### 액티브 오픈 호스트

`CLOSED → SYN-SENT → ESTABLISHED`

#### 패시브 오픈 호스트

`CLOSED → LISTEN → SYN-RECEIVED → ESTABLISHED`

### 연결 수립 과정 정리

| 호스트 A: 액티브 오픈 | 통신 | 호스트 B: 패시브 오픈 |
|---|---|---|
| CLOSED |  | CLOSED |
| SYN-SENT | SYN → | LISTEN |
|  | ← SYN+ACK | SYN-RECEIVED |
| ESTABLISHED | ACK → | ESTABLISHED |

---

## 19. 연결 종료 과정의 상태

### FIN-WAIT-1

액티브 클로즈 호스트가 FIN을 전송한 후 상대방의 ACK나 FIN을 기다리는 상태이다.

### FIN-WAIT-2

FIN-WAIT-1 상태에서 자신의 FIN에 대한 ACK를 받은 상태이다.

이후 상대방의 FIN을 기다린다.

### CLOSE-WAIT

상대방의 FIN을 받은 패시브 클로즈 호스트가 ACK를 전송한 후 자신의 애플리케이션이 연결 종료를 준비하는 상태이다.

CLOSE-WAIT가 지나치게 오래 유지된다면 프로그램이 소켓을 제대로 닫지 않았을 가능성이 있다.

### LAST-ACK

CLOSE-WAIT 상태의 호스트가 자신의 FIN을 전송한 뒤 마지막 ACK를 기다리는 상태이다.

### CLOSING

양쪽 호스트가 거의 동시에 FIN을 전송한 경우 볼 수 있는 상태이다.

- 자신의 FIN에 대한 ACK는 아직 받지 못함
- 상대방의 FIN은 수신한 상태

### TIME-WAIT

액티브 클로즈 호스트가 상대방의 FIN을 받고 마지막 ACK를 전송한 후 일정 시간 기다리는 상태이다.

일정 시간이 지나면 CLOSED 상태로 전환된다.

### 연결 종료 상태 변화

#### 액티브 클로즈 호스트

`ESTABLISHED → FIN-WAIT-1 → FIN-WAIT-2 → TIME-WAIT → CLOSED`

#### 패시브 클로즈 호스트

`ESTABLISHED → CLOSE-WAIT → LAST-ACK → CLOSED`

---

## 20. TCP 전체 상태 흐름

### 서버의 연결 수립

`CLOSED → LISTEN → SYN-RECEIVED → ESTABLISHED`

### 클라이언트의 연결 수립

`CLOSED → SYN-SENT → ESTABLISHED`

### 액티브 클로즈

`ESTABLISHED → FIN-WAIT-1 → FIN-WAIT-2 → TIME-WAIT → CLOSED`

### 패시브 클로즈

`ESTABLISHED → CLOSE-WAIT → LAST-ACK → CLOSED`

### 동시 종료가 발생한 경우

`ESTABLISHED → FIN-WAIT-1 → CLOSING → TIME-WAIT → CLOSED`

### 전체 상태 정리

| 상태 | 의미 |
|---|---|
| CLOSED | 연결 없음 |
| LISTEN | 연결 요청 대기 |
| SYN-SENT | SYN 전송 후 SYN+ACK 대기 |
| SYN-RECEIVED | SYN+ACK 전송 후 ACK 대기 |
| ESTABLISHED | 연결 확립 및 데이터 송수신 가능 |
| FIN-WAIT-1 | FIN 전송 후 ACK 또는 FIN 대기 |
| FIN-WAIT-2 | FIN에 대한 ACK 수신 후 상대방 FIN 대기 |
| CLOSE-WAIT | 상대방 FIN 수신 후 애플리케이션 종료 대기 |
| LAST-ACK | FIN 전송 후 마지막 ACK 대기 |
| CLOSING | 양쪽이 거의 동시에 FIN을 전송한 상태 |
| TIME-WAIT | 마지막 ACK 전송 후 일정 시간 대기 |

---

## 21. TIME-WAIT가 필요한 이유

액티브 클로즈 호스트는 마지막 ACK를 보낸 직후 즉시 연결 정보를 제거하지 않고 일정 시간 TIME-WAIT 상태로 기다린다.

주요 이유는 다음과 같다.

### 마지막 ACK의 재전송

액티브 클로즈 호스트가 전송한 마지막 ACK가 손실될 수 있다.

그러면 상대방은 FIN을 다시 전송한다.

TIME-WAIT 상태를 유지하고 있어야 재전송된 FIN에 다시 ACK로 응답할 수 있다.

### 지연된 패킷 제거

이전 연결에서 전송된 패킷이 네트워크에 남아 늦게 도착할 수 있다.

일정 시간 기다려 이전 연결의 패킷이 사라지도록 함으로써 새로운 연결의 패킷과 섞이는 것을 방지한다.

> TIME-WAIT는 오류가 아니라 TCP 연결을 안전하게 종료하기 위한 정상적인 상태이다.

| TIME-WAIT | 연결 종료 후 지연된 패킷을 처리하기 위해 대기 중 |

# 04-2-2 UDP

## 23. UDP의 특징

UDP는 비연결형 통신을 수행하는 전송 계층 프로토콜이다.

TCP와 달리 다음 기능을 기본적으로 수행하지 않는다.

- 연결 수립
- 연결 종료
- 수신 여부 확인
- 손실 데이터 재전송
- 데이터 순서 보장
- 흐름 제어
- 혼잡 제어
- 연결 상태 관리

UDP는 연결 상태를 유지하지 않으므로 **스테이트리스 프로토콜(Stateless Protocol)**이라고 한다.

### UDP의 장점

- 헤더 구조가 단순하다.
- 연결 수립 과정이 없다.
- 추가적인 제어 작업이 적다.
- TCP보다 오버헤드가 적다.
- 데이터를 빠르게 처리할 수 있다.
- 실시간성이 중요한 통신에 적합하다.

### UDP의 단점

- 데이터 도착을 보장하지 않는다.
- 데이터의 순서를 보장하지 않는다.
- 손실된 데이터를 자동으로 재전송하지 않는다.
- 중복된 데이터가 도착할 수 있다.

---

## 24. UDP 데이터그램 구조

UDP에서 송수신하는 데이터 단위를 **UDP 데이터그램**이라고 한다.

UDP 헤더는 총 8바이트로 구성된다.

| 필드 | 크기 | 역할 |
|---|---:|---|
| 송신지 포트 | 16비트 | 데이터를 보낸 프로세스 식별 |
| 수신지 포트 | 16비트 | 데이터를 받을 프로세스 식별 |
| 길이 | 16비트 | UDP 헤더와 페이로드의 전체 길이 |
| 체크섬 | 16비트 | UDP 데이터그램의 오류 검출 |

### UDP 헤더 구조

| 첫 번째 32비트 | 송신지 포트 16비트 | 수신지 포트 16비트 |
|---|---|---|
| 두 번째 32비트 | 길이 16비트 | 체크섬 16비트 |

UDP 헤더의 기본 크기:

`16비트×4=64비트=8바이트`

TCP의 기본 헤더가 20바이트인 것과 비교하면 UDP 헤더는 매우 단순하다.

---

## 25. UDP가 사용되는 분야

UDP는 일부 데이터가 손실되더라도 지연을 줄이는 것이 더 중요한 경우에 사용된다.

대표적인 사용 사례:

- 실시간 영상 스트리밍
- 실시간 음성 통화
- 인터넷 전화
- 온라인 게임
- DNS 질의
- DHCP
- 실시간 방송
- 멀티캐스트 통신

### 실시간 통신에서 UDP를 사용하는 이유

실시간 음성 통화에서 오래된 음성 데이터가 손실되었다고 가정한다.

TCP처럼 손실된 데이터를 다시 받을 때까지 기다리면 통화가 끊기거나 지연될 수 있다.

이 경우에는 손실된 과거 데이터를 재전송받는 것보다 다음 음성 데이터를 빠르게 받는 것이 더 중요하다.

---

## 26. UDP도 신뢰성을 제공할 수 있는가?

UDP 자체는 신뢰성 있는 전송을 제공하지 않는다.

하지만 UDP를 사용하는 응용 프로그램이 다음 기능을 직접 구현할 수 있다.

- 데이터 수신 확인
- 손실 데이터 재전송
- 데이터 순서 정렬
- 중복 데이터 제거
- 혼잡 제어

따라서 다음과 같이 구분해야 한다.

> UDP 프로토콜 자체는 신뢰성을 보장하지 않지만, UDP를 사용하는 응용 프로그램이 필요한 신뢰성 기능을 구현할 수 있다.

현대의 QUIC 프로토콜도 UDP 위에서 동작하면서 응용 계층에서 신뢰성, 암호화, 혼잡 제어 등의 기능을 제공한다.

---

## 27. TCP와 UDP 선택 기준

### TCP가 적합한 경우

데이터가 정확하고 순서대로 도착하는 것이 중요한 경우이다.

- 파일 다운로드
- 웹 문서 전송
- 이메일 전송
- 데이터베이스 연결
- SSH 원격 접속
- 결제 정보 전송

### UDP가 적합한 경우

일부 데이터 손실보다 빠른 전송과 낮은 지연이 중요한 경우이다.

- 실시간 영상
- 음성 통화
- 온라인 게임
- DNS 질의
- 실시간 방송

### 선택 기준 정리

| 중요 조건 | 적합한 프로토콜 |
|---|---|
| 정확한 데이터 전달 | TCP |
| 데이터 순서 보장 | TCP |
| 손실 시 자동 재전송 | TCP |
| 빠른 전송 | UDP |
| 낮은 지연 | UDP |
| 실시간성 | UDP |
| 연결 상태 유지 | TCP |
| 단순한 요청과 응답 | UDP 사용 가능 |

# 정보처리기사 핵심 정리

1. TCP는 연결형이고 UDP는 비연결형이다.
2. TCP는 신뢰성 있는 통신을 제공한다.
3. UDP는 신뢰성을 기본적으로 보장하지 않는다.
4. TCP는 스테이트풀, UDP는 스테이트리스 프로토콜이다.
5. TCP 통신은 연결 수립, 데이터 송수신, 연결 종료 단계로 이루어진다.
6. TCP 연결 수립에는 3-way handshake가 사용된다.
7. TCP 연결 종료에는 일반적으로 4-way handshake가 사용된다.
8. MSS는 TCP로 전송할 수 있는 최대 페이로드 크기이다.
9. MSS에는 TCP 헤더와 IP 헤더가 포함되지 않는다.
10. 일반적인 IPv4 TCP 환경에서 `MSS=MTU-20-20`으로 계산할 수 있다.
11. 이더넷 MTU가 1500바이트이면 일반적인 MSS는 1460바이트이다.
12. 순서 번호는 세그먼트 데이터의 첫 번째 바이트에 부여된 번호이다.
13. 다음 순서 번호는 현재 순서 번호에 전송한 데이터의 바이트 수를 더하여 계산한다.
14. 확인 응답 번호는 다음으로 수신하기를 기대하는 순서 번호이다.
15. 데이터 수신 시 ACK 번호는 일반적으로 순서 번호에 수신한 바이트 수를 더한 값이다.
16. SYN과 FIN은 순서 번호를 1만큼 소비한다.
17. ACK는 승인, SYN은 연결 수립, FIN은 정상적인 연결 종료를 의미한다.
18. RST는 연결을 강제로 초기화할 때 사용한다.
19. 윈도우 필드는 수신자가 추가로 받을 수 있는 데이터의 양을 나타낸다.
20. 액티브 오픈 호스트는 연결을 먼저 요청한다.
21. 패시브 오픈 호스트는 연결 요청을 기다린다.
22. LISTEN은 서버가 SYN을 기다리는 상태이다.
23. SYN-SENT는 SYN 전송 후 SYN+ACK를 기다리는 상태이다.
24. SYN-RECEIVED는 SYN+ACK 전송 후 ACK를 기다리는 상태이다.
25. ESTABLISHED는 TCP 연결이 확립된 상태이다.
26. CLOSE-WAIT는 상대방의 FIN에 ACK한 후 프로그램의 종료를 기다리는 상태이다.
27. TIME-WAIT는 마지막 ACK 전송 후 일정 시간 기다리는 상태이다.
28. TIME-WAIT는 마지막 ACK 재전송과 지연 패킷 제거를 위해 필요하다.
29. UDP 헤더의 기본 크기는 8바이트이다.
30. UDP 헤더는 송신지 포트, 수신지 포트, 길이, 체크섬으로 구성된다.

# 핵심 암기 문장

> TCP는 연결형·신뢰성·스테이트풀이고, UDP는 비연결형·빠른 전송·스테이트리스이다.

> MSS는 TCP 페이로드의 최대 크기이며, 일반적인 IPv4 환경에서는 MTU에서 IP 헤더와 TCP 헤더를 뺀 값이다.

> TCP 순서 번호는 데이터의 첫 바이트 번호이고, ACK 번호는 다음으로 받고 싶은 바이트 번호이다.

> SYN과 FIN은 데이터가 없어도 순서 번호를 1만큼 소비한다.

> 연결 수립은 SYN → SYN+ACK → ACK의 3-way handshake이다.

> 연결 종료는 FIN → ACK → FIN → ACK의 4-way handshake이다.

> 액티브 종료 상태는 FIN-WAIT-1 → FIN-WAIT-2 → TIME-WAIT이고, 패시브 종료 상태는 CLOSE-WAIT → LAST-ACK이다.
