## 03 네트워크 계층

네트워크 계층은 서로 다른 LAN 사이에서 패킷을 전달하기 위한 계층이다.

핵심 기능은 다음 두 가지이다.

- IP 주소를 이용한 송수신지 지정
- 라우팅을 통한 다른 네트워크와의 통신


# 03-1 LAN을 넘어서는 네트워크 계층

## 1. 데이터 링크 계층의 한계

물리 계층과 데이터 링크 계층만으로는 같은 LAN 안에서 통신할 수 있지만, LAN을 넘어 다른 네트워크의 호스트와 통신하기는 어렵다.

그 이유는 크게 두 가지이다.

### 한계 1 다른 네트워크까지의 경로를 알 수 없다

데이터 링크 계층의 스위치는 같은 LAN 안에서 MAC 주소를 이용해 프레임을 전달한다.

하지만 목적지가 다른 네트워크에 있으면 어떤 네트워크와 라우터를 거쳐야 하는지 결정해야 한다.

이를 위해 네트워크 계층에서는 라우팅을 사용한다.

- 라우팅(routing): 패킷이 목적지까지 이동할 경로를 결정하는 것
- 라우터(router): 라우팅을 수행하고 서로 다른 네트워크를 연결하는 장비
- 라우팅 테이블(routing table): 목적지 네트워크별 이동 경로가 기록된 정보

### 한계 2 MAC 주소만으로 전체 네트워크의 위치를 알기 어렵다

MAC 주소는 네트워크 인터페이스를 식별하는 물리적 주소이다.

하지만 MAC 주소 자체에는 호스트가 어느 네트워크에 속해 있는지를 나타내는 구조적인 위치 정보가 없다.

따라서 인터넷처럼 수많은 네트워크가 연결된 환경에서는 MAC 주소만으로 목적지의 위치와 경로를 찾기 어렵다.

네트워크 계층에서는 IP 주소를 이용하여 호스트가 속한 네트워크와 호스트를 구분한다.


## 2. IP 주소와 MAC 주소 비교

| 구분 | IP 주소 | MAC 주소 |
|---|---|---|
| 역할 | 목적지가 속한 네트워크와 호스트 지정 | 같은 LAN에서 네트워크 인터페이스 식별 |
| 비유 | 택배를 보낼 주소 | 택배를 실제로 받을 사람 |
| 주소 종류 | 논리 주소 | 물리 주소 |
| 계층 | 네트워크 계층 | 데이터 링크 계층 |
| 변경 가능성 | 네트워크에 따라 변경 가능 | 일반적으로 NIC마다 부여 |
| 할당 방법 | DHCP 자동 할당 또는 수동 설정 | 일반적으로 제조 과정에서 부여 |
| 사용 범위 | 서로 다른 네트워크 사이의 통신 | 같은 LAN 안에서의 프레임 전달 |

IP 주소와 MAC 주소는 둘 중 하나만 사용하는 것이 아니라 함께 사용한다.

IP 주소
→ 최종 목적지가 어느 네트워크에 있는지 판단

MAC 주소
→ 현재 LAN에서 다음 장비에게 프레임 전달

패킷이 여러 라우터를 거쳐 이동하더라도 일반적으로 송신지와 수신지 IP 주소는 유지된다.

반면 데이터 링크 계층의 송신지와 수신지 MAC 주소는 각 네트워크 구간을 지날 때마다 변경된다.


## 3. DHCP

DHCP는 Dynamic Host Configuration Protocol의 약자이다.

호스트에 네트워크 설정을 자동으로 할당하는 프로토콜이다.

DHCP를 통해 일반적으로 다음 정보를 받을 수 있다.

- IP 주소
- 서브넷 마스크
- 기본 게이트웨이
- DNS 서버 주소
- IP 주소 임대 시간

따라서 사용자가 IP 주소를 직접 설정하지 않아도 네트워크에 연결하면 필요한 정보를 자동으로 할당받을 수 있다.


## 4. 네트워크 계층의 핵심 IP

IP는 Internet Protocol의 약자이다.

IP는 물리 계층과 데이터 링크 계층만으로 해결하기 어려운 다음 문제를 해결한다.

- IP 주소를 이용한 송수신지 지정
- 서로 다른 네트워크 사이의 패킷 전달
- 라우터를 통한 경로 선택
- 필요한 경우 패킷 단편화

IP의 대표적인 버전은 다음과 같다.

- IPv4
- IPv6

IP는 신뢰성을 보장하지 않는 비연결형 프로토콜이다.

즉, IP 자체는 다음 내용을 보장하지 않는다.

- 패킷이 반드시 목적지에 도착하는 것
- 패킷이 순서대로 도착하는 것
- 패킷이 중복되지 않는 것
- 손실된 패킷을 다시 전송하는 것

신뢰성 있는 전송이 필요하면 상위 계층의 TCP 등을 함께 사용한다.


## 5. IP의 주요 기능

### 주소 지정 IP Addressing

IP 주소를 이용하여 송신지와 수신지를 지정하는 기능이다.

IPv4 주소는 4바이트, 즉 32비트로 구성된다.

8비트씩 네 부분으로 나누어 10진수로 표현하고 각 부분은 점으로 구분한다.

각각의 8비트 부분을 옥텟(octet)이라고 한다.

192.168.0.10

192 → 8비트  
168 → 8비트  
0 → 8비트  
10 → 8비트  

총 32비트 = 4바이트

각 옥텟은 8비트이므로 표현할 수 있는 값의 범위는 0부터 255까지이다.

### 단편화 IP Fragmentation

IP 단편화는 전송하려는 IP 패킷의 크기가 통신 매체의 MTU보다 클 때 패킷을 여러 개의 작은 패킷으로 나누는 것이다.

단편화된 패킷은 독립적으로 전송되며 수신지에 도착한 뒤 원래 데이터로 재조립된다.


## 6. MTU

MTU는 Maximum Transmission Unit의 약자이다.

하나의 통신 매체가 한 번에 전송할 수 있는 IP 패킷의 최대 크기이다.

일반적인 이더넷 환경의 MTU는 1500바이트이다.

MTU에는 IP 헤더도 포함된다.

이더넷 MTU 1500바이트  
= IP 헤더 + IP 데이터

IPv4 헤더가 기본 20바이트라면 단편화 없이 담을 수 있는 IP 데이터는 최대 1480바이트이다.

1500바이트 - IPv4 헤더 20바이트  
= 데이터 1480바이트

단, TCP나 UDP까지 고려하면 응용 프로그램이 실제로 보낼 수 있는 데이터 크기는 더 작아진다.


## 7. RFC 문서

RFC는 Request for Comments의 약자이다.

인터넷과 네트워크 기술에 관한 규칙, 제안, 실험 결과와 표준 등을 기록한 문서이다.

각 RFC에는 고유한 번호가 부여된다.

예시:

- RFC 791: IPv4
- RFC 8200: IPv6
- RFC 826: ARP

일부 RFC는 인터넷 표준으로 채택된다.

기존 RFC 문서는 출판된 후 내용을 직접 수정하지 않는 것이 원칙이다.

대신 오류 정보가 추가되거나 새로운 RFC가 기존 RFC를 갱신 또는 대체할 수 있다.

따라서 모든 RFC가 현재도 유효한 최종 표준인 것은 아니다.

- Updates: 기존 RFC의 일부를 갱신
- Obsoletes: 기존 RFC를 대체
- Errata: 발견된 오류에 대한 정정 정보

## 3. 식별자 Identification

식별자는 IPv4 패킷에 할당되는 번호이다.

하나의 원본 패킷이 여러 패킷으로 단편화되면 각각의 단편은 같은 식별자 값을 가진다.

수신지는 식별자를 통해 여러 단편이 어떤 원본 패킷에서 나누어진 것인지 구분한다.

원본 패킷 식별자 = 100

단편 1 → 식별자 100  
단편 2 → 식별자 100  
단편 3 → 식별자 100


## 4. 플래그 Flags

IPv4의 플래그 필드는 3비트로 구성된다.

[예약 비트][DF][MF]

### 예약 비트

현재 사용하지 않는 비트로 항상 0이다.

### DF Don’t Fragment

패킷을 단편화하지 말라는 의미이다.

- DF = 1: 단편화 금지
- DF = 0: 필요하면 단편화 가능

DF가 1인 패킷이 더 작은 MTU를 가진 경로를 만나면 라우터는 패킷을 단편화하지 못하므로 폐기하고 오류 메시지를 보낼 수 있다.

### MF More Fragments

뒤에 단편화된 패킷이 더 남아 있는지를 나타낸다.

- MF = 1: 뒤에 단편이 더 있음
- MF = 0: 마지막 단편이거나 단편화되지 않은 패킷

단편 1 → MF = 1  
단편 2 → MF = 1  
단편 3 → MF = 0


## 5. 단편화 오프셋 Fragment Offset

단편화 오프셋은 단편이 원본 데이터의 어느 위치에 있었는지를 나타낸다.

단편들은 서로 다른 경로로 이동할 수 있으므로 수신지에 순서대로 도착한다는 보장이 없다.

수신지는 단편화 오프셋을 이용하여 각 단편의 원래 순서를 파악하고 재조립한다.

단편화 오프셋은 바이트 위치를 그대로 기록하는 것이 아니라 8바이트 단위로 저장한다.

예시:

원본 데이터

0 ───────── 1480 ───────── 2960

단편 1  
오프셋 = 0

단편 2  
실제 시작 위치 = 1480바이트  
오프셋 = 1480 ÷ 8 = 185

단편 3  
실제 시작 위치 = 2960바이트  
오프셋 = 2960 ÷ 8 = 370

단편화와 재조립에 사용되는 핵심 필드는 다음 세 가지이다.

- 식별자: 어떤 원본 패킷에 속하는가?
- MF 플래그: 뒤에 단편이 더 있는가?
- 단편화 오프셋: 원본 데이터의 어느 위치인가?


## 6. IPv4 단편화 예시

원본 IP 패킷의 전체 크기가 4000바이트라고 가정한다.

IPv4 헤더는 20바이트이고 MTU는 1500바이트이다.

원본 데이터의 크기는 다음과 같다.

4000 - 20 = 3980바이트

한 단편에 들어갈 수 있는 최대 데이터는 다음과 같다.

1500 - 20 = 1480바이트

| 단편 | 데이터 크기 | 전체 크기 | 오프셋 | MF |
|---|---:|---:|---:|---:|
| 1 | 1480바이트 | 1500바이트 | 0 | 1 |
| 2 | 1480바이트 | 1500바이트 | 185 | 1 |
| 3 | 1020바이트 | 1040바이트 | 370 | 0 |

각 단편에는 별도의 IPv4 헤더가 붙는다.

따라서 단편화가 발생하면 헤더가 증가하고 트래픽과 처리 부하도 늘어난다.


## 7. TTL

TTL은 Time To Live의 약자이다.

패킷이 네트워크에 무한히 남아 순환하는 것을 방지하기 위한 수명 값이다.

패킷이 라우터를 하나 거칠 때마다 TTL이 1씩 감소한다.

TTL이 0이 되면 라우터는 해당 패킷을 폐기한다.

송신 시 TTL = 4

송신지  
↓  
라우터 1 통과 → TTL 3  
↓  
라우터 2 통과 → TTL 2  
↓  
라우터 3 통과 → TTL 1  
↓  
라우터 4 통과 → TTL 0 → 패킷 폐기

홉(hop)은 패킷이 이동하는 과정에서 거치는 라우터 단계를 의미한다.

일반적으로 라우터 하나를 통과하는 것을 한 홉이라고 한다.

`tracert` 또는 `traceroute` 명령어는 TTL의 특성을 이용하여 목적지까지 거치는 라우터를 확인한다.


## 8. 프로토콜 Protocol

프로토콜 필드는 IPv4 패킷의 데이터 부분에 어떤 상위 계층 프로토콜이 들어 있는지를 나타낸다.

| 번호 | 프로토콜 |
|---:|---|
| 1 | ICMP |
| 6 | TCP |
| 17 | UDP |

프로토콜 필드의 값이 6이면 IPv4 패킷의 페이로드에 TCP 세그먼트가 들어 있다는 의미이다.


## 9. 송신지와 수신지 IPv4 주소

송신지 IP 주소 필드에는 패킷을 보낸 호스트의 IPv4 주소가 들어간다.

수신지 IP 주소 필드에는 최종 목적지 호스트의 IPv4 주소가 들어간다.

라우터는 주로 수신지 IP 주소와 라우팅 테이블을 확인하여 패킷을 다음 경로로 전달한다.


## 10. IPv4 헤더 체크섬

IPv4 헤더 체크섬은 IPv4 헤더에 오류가 발생했는지 검사하는 필드이다.

IPv4 헤더의 TTL은 라우터를 지날 때마다 감소한다.

TTL 값이 바뀌면 헤더 내용도 바뀌므로 라우터는 헤더 체크섬을 다시 계산한다.

IPv4 헤더 체크섬은 데이터 전체가 아니라 IPv4 헤더의 오류를 검사한다.


# 03-3 IPv6

## 1. IPv6이 필요한 이유

IPv4 주소는 32비트로 구성된다.

이론적으로 표현할 수 있는 IPv4 주소 개수는 다음과 같다.

2³²개  
= 약 43억 개

컴퓨터, 스마트폰, 서버와 각종 IoT 장치가 증가하면서 약 43억 개의 IPv4 주소만으로는 모든 장치에 고유한 주소를 할당하기 어렵게 되었다.

IPv4 주소 고갈 문제를 해결하기 위해 IPv6가 등장했다.

NAT, 사설 IP 주소, DHCP 등의 기술로 IPv4 주소를 효율적으로 사용하고 있지만 근본적인 주소 부족 문제를 해결하는 기술은 IPv6이다.


## 2. IPv6 주소

IPv6 주소는 16바이트, 즉 128비트로 구성된다.

16비트씩 8개 그룹으로 나누어 16진수로 표현하고 각 그룹은 콜론으로 구분한다.

2001:0db8:0000:0000:0000:ff00:0042:8329

IPv6가 이론적으로 표현할 수 있는 주소 개수는 다음과 같다.

2¹²⁸개

이는 사실상 무한에 가까운 매우 큰 주소 공간이다.


## 3. IPv6 주소 축약

### 각 그룹 앞의 0 생략

0db8 → db8  
0042 → 42  
0000 → 0

### 연속된 0 그룹을 이중 콜론으로 생략

2001:0db8:0000:0000:0000:ff00:0042:8329

→ 2001:db8::ff00:42:8329

이중 콜론 `::`은 하나의 IPv6 주소에서 한 번만 사용할 수 있다.

여러 번 사용하면 생략된 0 그룹의 개수를 판단할 수 없기 때문이다.


## 4. IPv6 기본 헤더

[버전][트래픽 클래스][플로 레이블]

[페이로드 길이][다음 헤더][홉 제한]

[송신지 IPv6 주소]

[수신지 IPv6 주소]

[페이로드]

IPv6 기본 헤더는 고정된 40바이트 크기이다.

IPv4보다 주소는 훨씬 길지만 기본 헤더 구조는 단순화되었다.


## 5. 다음 헤더 Next Header

다음 헤더는 IPv6 기본 헤더 다음에 어떤 내용이 오는지를 나타낸다.

다음과 같은 내용을 가리킬 수 있다.

- TCP
- UDP
- ICMPv6
- IPv6 확장 헤더

IPv4의 프로토콜 필드와 비슷한 역할을 하지만 IPv6에서는 확장 헤더를 연결하는 데도 사용된다.


## 6. IPv6 확장 헤더

IPv6는 기본 헤더 뒤에 필요한 확장 헤더를 추가할 수 있다.

확장 헤더는 IPv6 기본 헤더와 상위 계층 데이터 사이에 위치한다.

IPv6 기본 헤더  
↓  
확장 헤더 1  
↓  
확장 헤더 2  
↓  
TCP 또는 UDP 등의 상위 계층 데이터

각 헤더의 다음 헤더 필드가 다음에 오는 헤더를 가리킨다.

IPv6 기본 헤더  
다음 헤더 = 라우팅 확장 헤더  
↓  
라우팅 확장 헤더  
다음 헤더 = 단편화 확장 헤더  
↓  
단편화 확장 헤더  
다음 헤더 = TCP  
↓  
TCP 세그먼트

확장 헤더는 꼬리에 꼬리를 무는 형태로 여러 개 연결될 수 있다.

대표적인 확장 헤더:

- Hop-by-Hop Options Header
- Routing Header
- Fragment Header
- Destination Options Header
- Authentication Header
- Encapsulating Security Payload Header


## 7. IPv6의 단편화

IPv6에서는 IPv4와 단편화 방식이 다르다.

IPv4에서는 라우터가 필요하면 패킷을 단편화할 수 있다.

IPv6에서는 중간 라우터가 패킷을 단편화하지 않는다.

패킷이 경로 MTU보다 크면 송신지가 크기를 줄이거나 송신지에서 직접 단편화해야 한다.

IPv6의 단편화는 단편화 확장 헤더를 통해 이루어진다.

단편화 확장 헤더에는 다음 정보가 포함된다.

- 다음 헤더
- 단편화 오프셋
- M 플래그
- 식별자

M 플래그는 IPv4의 MF 플래그와 비슷하다.

- M = 1: 뒤에 단편이 더 있음
- M = 0: 마지막 단편


## 8. 홉 제한 Hop Limit

홉 제한은 IPv4의 TTL과 비슷한 역할을 한다.

패킷이 라우터를 하나 거칠 때마다 값이 1씩 감소한다.

값이 0이 되면 패킷은 폐기된다.

IPv4 → TTL  
IPv6 → Hop Limit


## 9. 송신지와 수신지 IPv6 주소

송신지 IPv6 주소는 패킷을 보낸 호스트의 주소이다.

수신지 IPv6 주소는 최종 목적지 호스트의 주소이다.

라우터는 수신지 IPv6 주소를 바탕으로 패킷의 이동 경로를 결정한다.


## 10. IPv4와 IPv6 비교

| 구분 | IPv4 | IPv6 |
|---|---|---|
| 주소 길이 | 32비트, 4바이트 | 128비트, 16바이트 |
| 표현 방법 | 10진수 4개를 점으로 구분 | 16진수 8개 그룹을 콜론으로 구분 |
| 주소 개수 | 약 43억 개 | 2¹²⁸개 |
| 기본 헤더 크기 | 최소 20바이트 | 40바이트 고정 |
| 수명 필드 | TTL | Hop Limit |
| 상위 프로토콜 필드 | Protocol | Next Header |
| 헤더 체크섬 | 있음 | 없음 |
| 라우터 단편화 | 가능 | 불가능 |
| 단편화 정보 | 기본 헤더에 포함 | Fragment 확장 헤더 사용 |
| 브로드캐스트 | 사용 | 사용하지 않음 |
| 멀티캐스트 | 지원 | 지원 |
| 애니캐스트 | 제한적으로 사용 | 지원 |

IPv6에는 브로드캐스트가 없다.

IPv6에서는 브로드캐스트가 필요한 기능을 주로 멀티캐스트로 처리한다.


# 03-4 ARP

## 1. ARP란?

ARP는 Address Resolution Protocol의 약자이다.

IPv4 주소를 이용하여 같은 LAN에 있는 장치의 MAC 주소를 알아내는 프로토콜이다.

알고 있는 정보  
→ 상대방의 IPv4 주소

알아낼 정보  
→ 상대방 또는 다음 홉의 MAC 주소

ARP는 IPv4에서 사용한다.

IPv6에서는 ARP 대신 ICMPv6 기반의 NDP(Neighbor Discovery Protocol)를 사용한다.


## 2. ARP가 필요한 이유

IP 패킷을 이더넷으로 전송하려면 IP 패킷을 이더넷 프레임의 페이로드에 넣어야 한다.

이더넷 프레임에는 수신지 MAC 주소가 필요하다.

따라서 송신자는 목적지 또는 다음 홉의 IP 주소에 대응하는 MAC 주소를 알아야 한다.

상위 계층 데이터  
↓  
IP 패킷 생성  
↓  
이더넷 프레임에 넣어야 함  
↓  
수신지 MAC 주소 필요  
↓  
ARP로 IP 주소에 대응하는 MAC 주소 확인


## 3. 같은 네트워크의 호스트와 통신

호스트 A와 호스트 B가 같은 LAN에 있다고 가정한다.

호스트 A는 B의 IP 주소는 알고 있지만 MAC 주소는 모른다.

호스트 A

- IP 주소: 192.168.0.10
- MAC 주소: AA-AA-AA-AA-AA-AA

호스트 B

- IP 주소: 192.168.0.20
- MAC 주소: BB-BB-BB-BB-BB-BB

A가 B에게 프레임을 보내려면 B의 MAC 주소가 필요하다.


## 4. ARP 동작 과정

### 1단계 ARP 요청 ARP Request

호스트 A는 다음 질문이 담긴 ARP 요청을 전송한다.

“192.168.0.20을 사용하는 장치는 누구인가? MAC 주소를 알려 달라.”

호스트 A는 B의 MAC 주소를 모르기 때문에 ARP 요청을 브로드캐스트로 전송한다.

이더넷 수신지 MAC 주소:

FF:FF:FF:FF:FF:FF

브로드캐스트이므로 같은 LAN에 있는 모든 호스트가 ARP 요청을 받는다.

### 2단계 ARP 응답 ARP Reply

ARP 요청을 받은 호스트들은 요청에 들어 있는 대상 IP 주소를 확인한다.

- 자신의 IP 주소가 아니면 요청 무시
- 자신의 IP 주소라면 ARP 응답 전송

호스트 B는 자신의 MAC 주소를 담은 ARP 응답을 호스트 A에게 유니캐스트로 보낸다.

“192.168.0.20은 나다. 내 MAC 주소는 BB-BB-BB-BB-BB-BB이다.”

### 3단계 ARP 테이블 갱신

호스트 A는 ARP 응답을 받은 후 B의 IP 주소와 MAC 주소 관계를 ARP 테이블에 저장한다.

| IP 주소 | MAC 주소 |
|---|---|
| 192.168.0.20 | BB-BB-BB-BB-BB-BB |

이후에는 ARP 테이블에 저장된 정보를 사용하므로 매번 ARP 요청을 보낼 필요가 없다.


## 5. ARP 동작 흐름

호스트 A가 B의 IP 주소는 알지만 MAC 주소는 모름  
↓  
ARP 요청을 브로드캐스트  
↓  
같은 LAN의 모든 호스트가 요청 수신  
↓  
B를 제외한 호스트는 요청 무시  
↓  
호스트 B가 자신의 MAC 주소를 담아 유니캐스트 응답  
↓  
호스트 A가 B의 IP 주소와 MAC 주소를 ARP 테이블에 저장  
↓  
호스트 A가 B의 MAC 주소를 이용해 이더넷 프레임 전송


## 6. ARP 테이블

ARP 테이블은 IP 주소와 MAC 주소의 대응 관계를 저장한 표이다.

| IP 주소 | MAC 주소 | 유형 |
|---|---|---|
| 192.168.0.1 | 11-11-11-11-11-11 | 동적 |
| 192.168.0.20 | BB-BB-BB-BB-BB-BB | 동적 |

ARP 테이블의 동적 항목은 일정 시간이 지나면 삭제될 수 있다.

필요하다면 사용자가 직접 항목을 삭제할 수도 있다.

ARP 테이블에 목적지 정보가 이미 존재하면 새로운 ARP 요청을 보내지 않고 저장된 MAC 주소를 사용한다.

Windows에서 ARP 테이블 확인:

arp -a

Linux에서 확인:

ip neigh


## 7. 다른 네트워크의 호스트와 통신할 때 ARP

ARP는 같은 LAN 안에서만 동작한다.

목적지가 다른 네트워크에 있다면 송신자는 최종 목적지의 MAC 주소를 ARP로 알아내지 않는다.

대신 기본 게이트웨이인 라우터의 MAC 주소를 알아낸다.

예시:

호스트 A

- IP 주소: 192.168.0.10

목적지 서버

- IP 주소: 8.8.8.8

기본 게이트웨이

- IP 주소: 192.168.0.1
- MAC 주소: 11-11-11-11-11-11

호스트 A의 판단:

8.8.8.8은 내 네트워크에 속하지 않음  
↓  
기본 게이트웨이로 패킷을 보내야 함  
↓  
ARP로 192.168.0.1의 MAC 주소 확인  
↓  
이더넷 프레임의 수신지 MAC 주소에 기본 게이트웨이의 MAC 주소 입력

이때 주소는 다음과 같이 설정된다.

IP 패킷의 수신지 IP 주소  
= 최종 목적지 서버 8.8.8.8

이더넷 프레임의 수신지 MAC 주소  
= 현재 LAN의 기본 게이트웨이 MAC 주소


# 03-5 IP 단편화를 피하는 방법

## 1. 단편화의 문제점

IP 단편화는 가능하면 피하는 것이 좋다.

단편화가 발생하면 다음 문제가 생길 수 있다.

- 하나의 원본 패킷에 여러 IP 헤더가 추가됨
- 전송해야 하는 전체 데이터양 증가
- 불필요한 트래픽 발생
- 대역폭 낭비
- 송신지와 수신지의 처리 부하 증가
- 단편들을 재조립하는 과정 필요
- 단편 하나가 손실되어도 원본 패킷 전체를 정상적으로 재조립하기 어려움

따라서 패킷을 처음부터 경로에서 전달할 수 있는 크기로 보내는 것이 효율적이다.


## 2. 경로 MTU

경로 MTU(Path MTU)는 송신지에서 수신지까지 패킷이 이동하는 전체 경로에서 단편화 없이 전달할 수 있는 최대 패킷 크기이다.

송신지 ── MTU 1500 ── 라우터 1 ── MTU 1400 ── 라우터 2 ── MTU 1280 ── 수신지

이 경로의 MTU는 가장 작은 1280바이트이다.

경로 MTU  
= 경로에 존재하는 링크 중 가장 작은 MTU  
= 1280바이트


## 3. 경로 MTU 발견

경로 MTU 발견(Path MTU Discovery)은 송신지에서 수신지까지 단편화 없이 전달할 수 있는 최대 패킷 크기를 알아내는 과정이다.

### IPv4

1. 송신자가 DF 비트를 1로 설정하여 패킷 전송
2. 패킷이 MTU보다 작은 링크를 만남
3. 라우터가 패킷을 단편화할 수 없으므로 폐기
4. 라우터가 ICMP 오류 메시지를 송신자에게 전달
5. 송신자가 더 작은 크기로 다시 전송

### IPv6

IPv6 라우터는 패킷을 단편화하지 않는다.

패킷이 링크의 MTU보다 크면 라우터는 패킷을 폐기하고 ICMPv6 Packet Too Big 메시지를 송신자에게 보낸다.

송신자는 메시지를 바탕으로 패킷 크기를 줄여 다시 전송한다.


# 정보처리기사 핵심 정리

## 1. 네트워크 계층

- 서로 다른 네트워크 사이에서 패킷 전달
- IP 주소로 송수신지 지정
- 라우팅을 통해 이동 경로 결정
- 대표 장비는 라우터
- PDU는 패킷

## 2. IP 주소와 MAC 주소

IP 주소

- 논리 주소
- 네트워크 계층
- 최종 목적지와 네트워크 위치 식별

MAC 주소

- 물리 주소
- 데이터 링크 계층
- 같은 LAN에서 다음 장비 식별

## 3. IPv4

- 32비트
- 4바이트
- 점으로 구분된 4개의 10진수
- 각 옥텟의 범위는 0~255
- 이론적으로 약 43억 개의 주소 표현
- 기본 헤더는 최소 20바이트
- 헤더 체크섬 존재
- 라우터가 단편화할 수 있음

## 4. IPv4 단편화 핵심 필드

식별자  
= 단편들이 어떤 원본 패킷에 속하는지 구분

DF  
= 1이면 단편화 금지  
= 0이면 단편화 가능

MF  
= 1이면 뒤에 단편이 더 있음  
= 0이면 마지막 단편

단편화 오프셋  
= 원본 데이터에서 단편의 위치  
= 8바이트 단위

## 5. TTL

- 패킷의 수명
- 라우터를 통과할 때마다 1 감소
- 0이 되면 패킷 폐기
- 네트워크에서 패킷이 무한히 순환하는 것을 방지

## 6. IPv4 프로토콜 번호

ICMP = 1  
TCP = 6  
UDP = 17

## 7. IPv6

- 128비트
- 16바이트
- 콜론으로 구분된 8개의 16진수 그룹
- 기본 헤더는 40바이트
- TTL 대신 Hop Limit 사용
- Protocol 대신 Next Header 사용
- 기본 헤더 체크섬 없음
- 중간 라우터는 단편화하지 않음
- 송신지만 Fragment 확장 헤더를 이용하여 단편화 가능
- 브로드캐스트를 사용하지 않음
- IPv6에서 ARP 대신 NDP 사용

## 8. ARP

- IPv4 주소를 이용해 같은 LAN의 MAC 주소 확인
- ARP 요청은 브로드캐스트
- ARP 응답은 일반적으로 유니캐스트
- 결과는 ARP 테이블에 저장
- 다른 네트워크로 보낼 때는 최종 목적지가 아니라 기본 게이트웨이의 MAC 주소 확인

## 9. MTU와 경로 MTU

MTU  
= 하나의 링크가 전달할 수 있는 IP 패킷의 최대 크기

경로 MTU  
= 전체 경로에서 단편화 없이 전달 가능한 최대 크기  
= 경로에 존재하는 MTU 중 가장 작은 값


# 핵심 암기 문장

네트워크 계층은 IP 주소와 라우팅을 이용하여 서로 다른 네트워크 사이에서 패킷을 전달한다.

라우터는 수신지 IP 주소와 라우팅 테이블을 확인하여 패킷의 다음 경로를 결정한다.

MAC 주소는 같은 LAN에서 다음 장비를 식별하고, IP 주소는 최종 목적지와 네트워크 위치를 식별한다.

IPv4 주소는 32비트이고 IPv6 주소는 128비트이다.

IPv4의 DF가 1이면 단편화할 수 없고, MF가 1이면 뒤에 단편이 더 있다는 뜻이다.

단편화 오프셋은 원본 데이터에서 단편의 위치를 8바이트 단위로 나타낸다.

TTL은 라우터를 통과할 때마다 1씩 감소하며 0이 되면 패킷이 폐기된다.

IPv4에서 TCP의 프로토콜 번호는 6이고 UDP는 17이다.

IPv6의 다음 헤더는 상위 계층 프로토콜 또는 다음 확장 헤더를 나타낸다.

IPv6에서는 중간 라우터가 패킷을 단편화하지 않는다.

ARP 요청은 브로드캐스트이고 ARP 응답은 일반적으로 유니캐스트이다.

목적지가 다른 네트워크에 있으면 ARP로 최종 목적지의 MAC 주소가 아니라 기본 게이트웨이의 MAC 주소를 알아낸다.

IP 단편화를 피하려면 경로 MTU에 맞는 크기로 패킷을 전송해야 한다.
